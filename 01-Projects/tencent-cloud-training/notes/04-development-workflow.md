## 4.1 规约驱动的AI开发工作流（6阶段完整流转）

**截图参考**：`../images/AI编程的开发工作流.png`

传统AI编程的问题是"想到哪写到哪"，规约驱动工作流强调**每个阶段都有明确的输入/输出物和AI参与规范**：

```
┌──────────┐   ┌──────────┐   ┌──────────────────────┐   ┌──────────┐   ┌──────┐   ┌──────┐
│  阶段1    │→  │  阶段2    │→  │  阶段3（核心循环）      │→  │  阶段4   │→  │ 阶段5 │→  │ 阶段6 │
│  设计     │   │  开发     │   │                      │   │  联调测试 │   │ 发布  │   │ 评审  │
└──────────┘   └──────────┘   └──────────────────────┘   └──────────┘   └──────┘   └──────┘
```

### 各阶段详细说明

#### 阶段1：设计
| 项目 | 内容 |
|------|------|
| **输入** | 需求文档（PRD）、技术约束、参考架构 |
| **AI参与** | 方案对比、技术选型建议、风险评估 |
| **产出物** | `design.md` — 技术方案文档（含架构图） |
| **关键规范** | 必须有至少2个备选方案的对比分析 |

#### 阶段2：开发（含4个子循环）
这是AI参与最深的阶段，采用**需求理解 → 检索 → 拆解 → 人工批**的微循环：

| 子步骤 | AI做什么 | 人做什么 | 产出物 |
|--------|---------|---------|--------|
| **需求理解** | 复述需求、列出疑问、确认边界 | 确认理解无误、补充隐含需求 | `understanding.md` |
| **检索** | 搜索相关代码、文档、API定义 | 指定搜索范围 | 相关代码引用列表 |
| **拆解** | 将任务分解为2-15分钟的小步骤 | 确认拆解合理、调整优先级 | `plan.md` 执行计划 |
| **执行+人工批** | 按步骤逐个执行（每次~50行变更） | **每步审核后再允许下一步** | 可运行的代码 |

#### 阶段3：联调测试
| 项目 | 内容 |
|------|------|
| **AI参与** | 生成测试用例、构造Mock数据、执行集成测试 |
| **产出物** | 测试报告、覆盖率数据 |
| **关键规范** | 核心路径必须100%覆盖 |

#### 阶段4：发布
| 项目 | 内容 |
|------|------|
| **AI参与** | 生成Changelog、检查Breaking Changes、编写发布说明 |
| **产出物** | `CHANGELOG.md`、发布清单 |

#### 阶段5：评审（重要！）
| 项目 | 内容 |
|------|------|
| **参与者** | 人+AI联合评审 |
| **评审内容** | 代码质量、架构一致性、性能影响、安全性 |
| **产出物** | 评审记录 + Action Items |

**每个阶段的md产出物就是"规约"**——它既是本阶段的交付，也是下一阶段的输入。

## 4.2 Plan模式 + Memory系统

**截图参考**：`../images/AI编程的记忆.png`

### Plan模式：先想再做的纪律

Plan模式是一种强制AI"先制定计划、经确认后再执行"的工作模式：

| 维度 | 说明 |
|------|------|
| **触发条件** | 多模块改动、不确定最佳方案、复杂重构、预估超过30分钟的任务 |
| **流程** | 需求→计划输出→用户确认→分步执行→每步反馈 |
| **价值** | 避免AI"跑偏"、减少返工、保持人对方向的掌控 |
| **类比** | 就像建筑开工前必须有施工图纸，不能边想边建 |

### Memory系统：双层记忆架构

| 记忆类型 | 范围 | 存储位置 | 内容 | 持久性 |
|---------|------|----------|------|--------|
| **项目记忆（Project Memory）** | 当前项目内 | 项目根目录的规则文件（如CODEBUDDY.md） | 架构决策、编码规范、技术栈、约束条件 | 跨Session持久 |
| **用户记忆（User Memory）** | 跨项目全局 | 用户主目录（如 ~/.codebuddy/） | 偏好设置、常用模式、历史经验、个人信息 | 跨项目持久 |
| **会话记忆（Session Memory）** | 当前对话 | 对话上下文窗口 | 本次对话的完整历史 | Session内有效 |

**Memory的写入时机**：
- 项目记忆：在项目初始化、架构变更、规范更新时写入
- 用户记忆：在使用过程中逐步积累（如发现某个Pattern好用就记录下来）
- 会话记忆：自动维护，Session结束时可选择性地沉淀到持久记忆

### 与ContextStack的精确对应

| 腾讯云概念 | ContextStack对应 | 文件/目录 |
|-----------|-----------------|----------|
| Plan模式 | Brainstorming Skill（强制前置设计） | always规则 |
| 项目记忆 | PROJECT-RULES.md + STATE.md | 项目级 |
| 用户记忆 | GLOBAL-RULES.md + MEMORY.md | 全局级 |
| 会话记忆 | 工作台STATE.md中的session字段 | 会话级 |

## 4.3 极光框架（Jiguang Framework）架构

**截图参考**：`../images/编码-极光框架.png`

极光框架是一个面向编码任务的Agent框架，完整的请求处理链路：

```
┌──────┐    ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌───────┐   ┌─────────┐   ┌──────────┐
│调用方 │ →  │ MCP Tool │ → │ Skill函数 │ → │ Plasma   │ → │Device │ → │ Command  │ → │ 目标系统  │
│      │    │          │   │          │   │ 核心     │       │         │           │           │
└──────┘    └──────────┘   └──────────┘   └──────────┘   └───────┘   └─────────┘   └──────────┘

            标准化接口      业务逻辑封装    调度引擎       设备抽象    具体命令    执行目标
```

**各组件职责详解**：

| 组件 | 职责 | 设计要点 |
|------|------|----------|
| **调用方** | 发起请求的用户或上层系统 | 可以是人（CLI/GUI）也可以是其他系统（CI/CD webhook） |
| **MCP Tool** | Model Context Protocol工具层 | **标准化接口**——不同AI模型都能通过统一协议调用 |
| **Skill函数** | 封装特定领域的技能逻辑 | 如"H3C交换机配置"、"Git提交规范"、"代码审查"等 |
| **Plasma核心** | 框架调度引擎 | 负责：任务解析→Skill匹配→执行调度→结果聚合 |
| **Device** | 设备/目标抽象层 | 屏蔽底层差异（本地文件/远程服务器/网络设备/云服务） |
| **Command** | 最终执行的操作原子 | 最小粒度的执行单位，保证可追溯、可回滚 |

**设计亮点**：
1. **MCP协议**解耦了AI模型与具体工具，换模型不需要重写Skill
2. **Device抽象层**使得同一套Skill可以操作不同目标（本地/远程/设备）
3. **Plasma调度引擎**支持串行/并行/条件分支等多种执行模式

## 与ContextStack框架的关联

- **6阶段规约驱动工作流**可直接用于ContextStack的项目开发流程，每个阶段的md产出物对应工作台中的文件
- **Plan模式**与Brainstorming Skill的Phase 1-4（需求澄清→方案探索→设计输出→确认门控）完全同构
- **Memory双层架构**与ContextStack的全局规则(GLOBAL-RULES) + 项目规则(PROJECT-RULES) + 会话状态(STATE)三分法一一对应
- **极光框架的MCP+Skill+Device分层思想**与ContextStack的Rule+Skill+Memory分层理念异曲同工——都是通过分层实现解耦和复用

## 二、AI Coding 四大核心组件

| 组件 | 角色 | 一句话 | 核心职责 |
|:---:|------|-------|---------|
| **LLM** | 🧠 大脑 | 推理与生成 | 理解意图、生成代码、回答问题，是 AI 能力的底座 |
| **Agent** | 🤖 执行体 | 规划与行动 | 拆解任务、调用工具、多步执行、自纠错，让 AI 从"一句话回复"变成"自主完成任务" |
| **Skills** | 🛠 技能包 | 专业领域能力 | 封装领域知识和工作流（如 TDD、代码审查、调试），让 Agent 按工程规范做事 |
| **MCP** | 🔌 连接器 | 外部系统接入 | Model Context Protocol，标准化接入外部工具和系统（数据库、Git、API），让 Agent 具备"手" |

### 四者协作关系

```
用户需求 → Agent（规划）→ Skills（执行规范）→ MCP（调工具）→ LLM（生成输出）
              ↑_______________________________________________↓
                            反馈闭环
```

> **关键理解**：LLM 是"会不会"，Agent 是"能不能做"，Skills 是"做得好不好"，MCP 是"能做什么"。四者缺一不可。

## 三、AI 编程发展三阶段

```
阶段1: 辅助编码
├── 人仍然拆任务、找上下文、复制粘贴
├── AI 只站在开发者旁边，提升局部编码效率
└── 覆盖率先于深度

阶段2: 自然语言驱动代码生成
├── 开发者用意图、上下文和反馈驱动 AI 生成代码
├── 效率提升明显
└── 一致性与可维护性开始成为新问题

阶段3: 规格驱动开发 (SDD) ← 当前腾讯主推
├── 先把模糊需求沉淀为 Spec
├── 按规约执行与验收
├── 从工具能力 → 组织能力
└── 建立需求、架构、编码、测试、发布、审计闭环
```

> 三阶段**不可跳级**。不是装一个插件，而是研发方式升级。

## 四、核心方法论：从对话到 SDD

### 2.1 核心范式

```
旧范式：我跟AI对话 → AI直接改代码
新范式：需求 → Spec（可审查的技术共识）→ AI按规约执行
```

**客户真正买单的不是命令，而是背后那条可重复、可复盘的交付方法论。**

### 2.2 SDD 五步主链

| 步骤 | 行动 | 产品 |
|------|------|------|
| 1. **定义** | 把目标、边界、验收口径说清楚 | 需求文档 |
| 2. **澄清** | 把隐藏假设显性化，避免带误解设计方案 | Clarification 记录 |
| 3. **方案** | 沉淀实现方案、关键权衡与主要风险 | Design Plan |
| 4. **拆分** | 把方案拆成可执行、可追踪的任务切片 | Tasks.md |
| 5. **推送** | 推进执行，代码、测试、文档一起落地 | 可交付代码 |
| 6. **验证** | 查遗漏，形成交付前闭环 | 测试报告 |

### 2.3 Skills 驱动开发全流程

```
┌─────────────────────── 开发流程 ───────────────────────┐
│                                                         │
│  阶段         模式               Skill                   │
│  ──────      ──────           ──────────               │
│  需求分析    人+AI 协作        brainstorming (clarify)  │
│     ↓                                                    │
│  方案设计    AI 自动           writing-plans             │
│     ↓                                                    │
│  任务拆分    AI 自动           task-breakdown            │
│     ↓                                                    │
│  代码实现    AI 自动           implementing (TDD)        │
│     ↓                                                    │
│  代码审查    AI 自动           code-review               │
│     ↓                                                    │
│  提交代码    人确认            git-commit-msg            │
│                                                         │
└─────────────────────────────────────────────────────────┘

┌─────────────────────── 测试与交付 ───────────────────────┐
│                                                         │
│  阶段         模式               Skill                   │
│  ──────      ──────           ──────────               │
│  单元测试    AI 自动            test-generation          │
│     ↓                                                    │
│  集成测试    AI 自动            integration-test         │
│     ↓                                                    │
│  回归测试    AI 自动            regression-test          │
│     ↓                                                    │
│  文档生成    AI 自动            doc-generation           │
│     ↓                                                    │
│  PR 创建     AI 自动            pr-creation              │
│     ↓                                                    │
│  部署发布    人确认             deploy (人工触发)        │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

> **关键特征**：需求分析阶段是**人+AI 协作**（brainstorming clarify），其他阶段以 **AI 自动执行为主**，人只在关键节点确认（提交代码、部署发布）。

### 2.4 全流程自动化链路（13 Skills 闭环）

```
输入: 需求文档(PR/Markdown)
    ↓
Skill 1: 需求解析 ──────→ 结构化需求对象
    ↓
Skill 2: 工程初始化 ──────→ 项目工程结构
    ↓
Skill 3: 业务代码生成 ──────→ 高可用业务逻辑
    ↓
Skill 4: 代码落盘写入 ──────→ 本地代码文件 / 版本库
    ↓
Skill 5: 增量编译执行 ──────→ 编译结果报告与产物
    ↓
    ┌──→ 编译失败? ─────────────────────────┐
    │                                        ↓
    └─ Skill 6-8: 编译错误修复闭环 ←──────────┘
        (检测错误 → 智能修复 → 重新落盘)
    │
    ↓ 编译成功
    ↓
Skill 9-11: 校验、测试与交付
    (本地校验 → 远程部署与验收 → 生成交付报告)
    ↓
    ┌──→ 运行时问题? ───────────────────────┐
    │                                        ↓
    └─ Skill 12-13: 运行时自愈闭环 ←──────────┘
        (远程日志下载 → 日志分析 → 定位问题 → 回到代码生成修复)
```

**13 Skills 映射表：**

| Skill | 名称 | 角色 | 失败处理 |
|:---:|:---:|------|---------|
| 1 | 需求解析 | 将非结构化需求转为结构化对象 | 回退到人澄清 |
| 2 | 工程初始化 | 创建项目目录结构、配置、依赖 | 重试/换模板 |
| 3 | 业务代码生成 | 核心逻辑代码生成 | 分解任务重试 |
| 4 | 代码落盘写入 | 文件系统写入、Git 操作 | 冲突检测 |
| 5 | 增量编译执行 | 增量编译、产物生成 | 触发 6-8 |
| 6-8 | 编译错误修复闭环 | 错误识别、自动修复、验证 | 循环直到成功 |
| 9-11 | 测试与交付 | 本地测试→部署→验收报告 | 触发 12-13 |
| 12-13 | 运行时自愈闭环 | 日志采集→分析→定位→修复 | 二次修复循环 |

> **关键洞察**：这是一个**双闭环系统**——编译错误闭环（构建期）+ 运行时自愈闭环（运行期），覆盖了从需求到交付再到运维的**全生命周期**。

### 2.5 项目步骤详解(1/4)：开发准备 — Skill 01-03

#### Skill 01：需求解析

| 维度 | 内容 |
|------|------|
| **功能** | 将需求文档转为结构化的需求对象，确认描述、优先级、负责人等关键字段就绪 |
| **输入** | 需求文档（PR/Markdown），格式：`标题、详细描述、优先级` |
| **输出** | 结构化需求对象（编号、标题、状态、描述、优先级、负责人） |
| **案例** | 输入：`"我要配置一个 AI 模型页面的 web 产品需求文档"` → 输出：已录入系统的结构化需求 |
| **关键价值** | 需求直接进入研发系统，状态可追踪，无需二次补录 |

#### Skill 02：工程初始化

| 维度 | 内容 |
|------|------|
| **功能** | 根据需求信息创建项目工程结构、配置依赖、初始化版本控制 |
| **输入** | 需求文档 + 设计稿（如有） |
| **输出** | 完整的项目工程目录 + 依赖配置 + 开发环境就绪 |
| **案例** | 读取需求文档 + 设计稿文件 → 自动生成项目骨架 |
| **关键价值** | 从零到开发就绪一步到位，减少环境搭建时间 |

#### Skill 03：业务代码生成

| 维度 | 内容 |
|------|------|
| **功能** | 根据需求文档和设计稿，生成高可用业务逻辑代码 |
| **输入** | 需求文档（由 Skill 01 输出）+ 工程结构（由 Skill 02 输出） |
| **输出** | 可编译运行的业务代码 + 单元测试框架 |
| **案例** | 需求："创建用户管理模块（CRUD + 权限校验）" → AI 生成完整模块代码 |
| **关键价值** | 从"给建议"升级为"直接执行"，产品写需求→AI 出代码链式打通 |

> **三步联动**：需求解析 → 工程初始化 → 代码生成，形成"从对话到文档到代码"的完整链路。关键转变：AI 不再只给建议，而是**直接执行**代码生成动作。

### 2.6 项目步骤详解(2/4)：自动化测试 — Skill 09-11

| Skill | 名称 | 功能 | 输入 → 输出 |
|:---:|:---:|------|------------|
| 09 | 自动化测试 | 根据需求文档和设计稿生成测试用例并写入系统 | 需求文档 + 设计稿 → 测试用例（已录入） |
| 10 | 测试脚本生成 | 根据测试用例生成自动化测试脚本并运行 | 测试用例 → 自动化测试脚本 + 运行结果 |
| 11 | 端到端测试 | 编写端到端自动化测试用例，不同需求单独目录存放 | 测试用例 → E2E 测试脚本（新需求不重复生成已有脚本） |

### 2.7 项目步骤详解(3/4)：代码实现与修复 — Skill 06-08

| Skill | 名称 | 功能 | 触发条件 |
|:---:|:---:|------|---------|
| 06 | 错误检测 | 解析编译错误、运行时异常、测试失败日志 | 编译/测试失败时自动触发 |
| 07 | 智能修复 | 基于错误诊断，自动生成修复代码并替换 | Skill 06 输出错误信息后触发 |
| 08 | 验证回归 | 重新编译 + 运行测试，确认修复有效 | Skill 07 完成修复后自动触发 |

> **闭环机制**：06→07→08 循环直到所有错误修复，失败超过阈值时回退到人工介入。

### 2.8 项目步骤详解(4/4)：运行时自愈 — Skill 12-13

| Skill | 名称 | 功能 |
|:---:|:---:|------|
| 12 | 远程日志采集 | 从部署环境下拉运行日志、错误堆栈、性能指标 |
| 13 | 日志分析与修复 | 分析日志定位根因 → 生成修复代码 → 重新部署

    └── 可与 OpenSpec / SpecKit 同时叠用

## 六、六工种能力重组

| 工种 | 传统角色 | AI 介入后的角色 | 能力变化 |
|------|---------|---------------|---------|
| **需求/产品** | 写 PRD、录入系统 | 对话确认需求，AI 同步录入到系统 | 重心回到判断和取舍 |
| **架构** | 画架构图、写方案 | 沉淀架构红线、定义边界 | 守门员权重高于进攻手 |
| **研发** | 写代码、调试 | AI 执行，人驱动意图+反馈 | 从"写"→"审" |
| **质量/测试** | 写测试用例、手工测试 | AI 生成测试用例 + 自动化 | 把主观感觉变成可执行判定 |
| **PM** | 排期、跟踪 | **任务分发给数字员工和自然人** | 中心分发任务 |
| **运维** | 部署、监控 | 闭环延伸到构建、签名、制品、发布 | 最后一层连接能力 |

> 人机混合编队：数字员工跑吞吐，自然人做判断。

## 七、实战案例

### 7.1 知识库搜索 → 画布可视化展示

| 维度 | 内容 |
|------|------|
| **场景** | 从知识库中检索信息，将结果以可视化画布形式呈现，支持交互式浏览 |
| **输入** | 自然语言查询（如"展示所有安全相关的组件依赖关系"） |
| **流程** | ① 用户输入查询 → ② AI 解析意图 → ③ 知识库检索 → ④ 结果结构化 → ⑤ 画布渲染 |
| **输出** | 交互式可视化画布（节点 + 连线 + 属性面板） |
| **关键价值** | 从"搜索结果列表"→"可交互的关系图谱"，知识检索从文本升级为可视化 |

### 7.2 需求文档自动生成并录入系统

| 维度 | 内容 |
|------|------|
| **场景** | 产品经理通过对话描述需求，AI 自动生成结构化 PRD 并录入需求管理平台 |
| **输入** | 自然语言需求描述（如"我要配置一个 AI 模型页面的 web 产品"） |
| **流程** | ① 对话 clarify → ② 确认标题/优先级/验收标准 → ③ AI 生成结构化需求 → ④ 自动录入系统 |
| **输出** | 需求管理平台中已就绪的需求条目（编号、标题、状态、优先级、负责人齐全） |
| **关键价值** | 写需求的表单时间 > 写需求本身 → AI 接管表单，人回到判断和取舍 |

### 7.3 设计稿驱动开发

| 维度 | 内容 |
|------|------|
| **场景** | 从设计稿直接生成前端代码，设计与工程闭环 |
| **工具链** | Figma → Code（像素级转代码）、腾讯设计协同平台（组件资产沉淀）、AI 设计实验品（提示词出概念稿） |
| **关键价值** | 一句话生成设计稿，设计中出码，设计与工程闭环最顺滑 |

### 7.4 从历史项目接入到自动化测试全流程

| 维度 | 内容 |
|------|------|
| **场景** | 非新项目快速接入 AI 辅助开发 + 自动化测试 |
| **接入方式** | `codebuddy init` 快速接入，不支持的项目建议切换到推荐仓库形态 |
| **测试流程** | 研发端单元测试 → 测试团队自动化测试 → AI 生成测试用例 |
| **仓库选型** | Monorepo（新项目/中小团队/跨模块联动） vs Multirepo（存量/高复杂度/多团队并行） |

### 7.5 部门服务器维护知识库

| 维度 | 内容 |
|------|------|
| **场景** | 建立部门内服务器维护知识库，沉淀运维经验，方便组内共享和新人上手 |
| **痛点** | 服务器配置、部署流程、故障排查经验散落在个人脑中，离职即流失，新人重复踩坑 |
| **方案** | 将服务器维护的文档、脚本、配置、故障案例统一沉淀到知识库，AI 可检索并生成操作建议 |
| **流程** | ① 收集历史维护记录 → ② 结构化入库（文档/SOP/脚本） → ③ AI 对接知识库 → ④ 组员自然语言查询 → ⑤ AI 返回操作步骤或诊断建议 |
| **关键价值** | 从"问老员工"→"问知识库"，维护经验可复用、可追溯，新人上手时间从数周→数天 |

## 八、常见问题与解决方案

| 问题 | 根因 | 解决方案 |
|------|------|---------|
| **智能体修改了错误的文件** | 文件路径模糊，定位不精准 | 提供文件的**绝对路径**，明确文件名和所在目录，减少歧义 |
| **AI 修改后引入了新的编译错误** | 代码逻辑关联复杂，无法覆盖全量场景 | 使用**编译错误修复 Skill** 自动修复，或粘贴完整编译日志让 AI 定位解决 |
| **智能体没有理解业务意图** | 业务上下文缺失，指令描述简单 | 提供**完整的业务背景、设计标准**，并提供相关代码片段作为参考 |
| **代码搜索效率低** | 传统关键词匹配无法理解代码语义与逻辑 | 使用 **AI 驱动的代码搜索和语义理解**，快速定位目标代码片段 |
| **反复修改无效** | 缺乏关键线索，陷入无效的修改循环 | **打断当前修改循环**，补充运行环境信息、报错日志等关键线索，引导 AI 更换修复方向 |
| **代码风格与团队规范不一致** | AI 默认使用互联网开源项目通用写法，不知道团队编码规范 | 在 Prompt 中**嵌入团队编码规范**，或把规范固化为 **Skill 自动加载** |

## 九、常见 Q&A（售前/交付关键问题）

### 决策层

| 问题 | 腾讯回答 |
|------|---------|
| **ROI 怎么算？** | 积分制，按模型不同消耗不同倍率，腾讯内部平均 1200 积分/席位/月 参考 |
| **与竞品差异？** | 腾讯背书 + 长期路线图 + 大客户案例 + 稳定国内外模型资源 |
| **内部怎么推广？** | 配置足量积分给用户体验，比"集成性强"更重要 |
| **代码会泄漏吗？** | 数据分片传给大模型，云端不存储用户代码 |

### 技术层

| 问题 | 腾讯回答 |
|------|---------|
| **历史项目如何接入？** | `codebuddy init` 快速接入，不建议拍脑袋说"工期缩短 X 倍" |

| **模型怎么选？** | 海外模型（方案设计）+ 国产模型（执行），数据不出海 |
| **团队经验怎么沉淀？** | 通过 `MCP` 插件接入知识库，团队规则用 `CLAUDE.md` / `AGENTS.md` |

## 十、高效协作方法论：问对问题，按流程排查

### 9.1 与 AI 协作的 4 个原则

| # | 原则 | 说明 | 示例 |
|:---:|:---:|------|------|
| 01 | **精准定位** (Be Specific) | 避免宽泛描述，提供明确的上下文信息 | ❌ "我的代码出错了" → ✅ "`UserService.java` 第 45 行空指针，传入参数为 null" |
| 02 | **明确对比** (Show Contrast) | 清晰阐述"预期结果"与"实际结果"的差异 | "预期：返回用户列表；实际：抛出 `SQLSyntaxErrorException`" |
| 03 | **提供证据** (Provide Evidence) | 附上客观事实依据 | 粘贴完整报错日志、核心代码片段、网络请求记录 |
| 04 | **分步提问** (Step by Step) | 将复杂问题拆解为独立小问题 | 先确认环境 → 再确认配置 → 最后看代码逻辑 |

### 9.2 问题排查 3 步法

```
Step 1: 边界确认 (Boundary Check)
    ├── 影响范围：所有用户？特定用户？
    ├── 环境边界：线上？本地？测试环境？
    └── 模块边界：全功能？特定 API？
            ↓
Step 2: 环境对比 (Environment Contrast)  
    ├── 配置文件差异
    ├── 依赖版本差异
    ├── 环境变量差异
    └── 网络策略差异
            ↓
Step 3: 代码逻辑排查 (Code Logic)
    ├── Review 最近提交记录
    ├── 梳理关键逻辑分支
    └── 日志断点调试定位
```

> **核心洞察**：AI 不是万能的，**高质量的问题输入 → 高质量的答案输出**。遵循"4 原则 + 3 步法"，让 AI 成为你的高效排障搭档。

## 一、AI 编程发展三阶段

```
阶段1: 辅助编码
├── 人仍然拆任务、找上下文、复制粘贴
├── AI 只站在开发者旁边，提升局部编码效率
└── 覆盖率先于深度

阶段2: 自然语言驱动代码生成
├── 开发者用意图、上下文和反馈驱动 AI 生成代码
├── 效率提升明显
└── 一致性与可维护性开始成为新问题

阶段3: 规格驱动开发 (SDD) ← 当前腾讯主推
├── 先把模糊需求沉淀为 Spec
├── 按规约执行与验收
├── 从工具能力 → 组织能力
└── 建立需求、架构、编码、测试、发布、审计闭环
```

> 三阶段**不可跳级**。不是装一个插件，而是研发方式升级。

## 二、核心方法论：从对话到 SDD

### 2.1 核心范式

```
旧范式：我跟AI对话 → AI直接改代码
新范式：需求 → Spec（可审查的技术共识）→ AI按规约执行
```

**客户真正买单的不是命令，而是背后那条可重复、可复盘的交付方法论。**

### 2.2 SDD 五步主链

| 步骤 | 行动 | 产品 |
|------|------|------|
| 1. **定义** | 把目标、边界、验收口径说清楚 | 需求文档 |
| 2. **澄清** | 把隐藏假设显性化，避免带误解设计方案 | Clarification 记录 |
| 3. **方案** | 沉淀实现方案、关键权衡与主要风险 | Design Plan |
| 4. **拆分** | 把方案拆成可执行、可追踪的任务切片 | Tasks.md |
| 5. **推送** | 推进执行，代码、测试、文档一起落地 | 可交付代码 |
| 6. **验证** | 查遗漏，形成交付前闭环 | 测试报告 |

## 三、三层工具架构（图片已确认）

```
第1层：需求 → Spec（"要做什么"）
├── OpenSpec  — 以 Change Proposal 为单元，粒度小、成本低
└── Spec Kit  — 以 Feature 为单元，叙事强、三件套评审

第2层：Spec → 代码（"怎么做稳"）
└── SuperPowers / ECC — 给 Agent 装"工程纪律"
    ├── 强制 TDD + 子代理评审 + 提交前自检
    └── 可与 OpenSpec / SpecKit 同时叠用
```

## 四、六工种能力重组

| 工种 | 传统角色 | AI 介入后的角色 | 能力变化 |
|------|---------|---------------|---------|
| **需求/产品** | 写 PRD、录入系统 | 对话确认需求，AI 同步录入到系统 | 重心回到判断和取舍 |
| **架构** | 画架构图、写方案 | 沉淀架构红线、定义边界 | 守门员权重高于进攻手 |
| **研发** | 写代码、调试 | AI 执行，人驱动意图+反馈 | 从"写"→"审" |
| **质量/测试** | 写测试用例、手工测试 | AI 生成测试用例 + 自动化 | 把主观感觉变成可执行判定 |
| **PM** | 排期、跟踪 | **任务分发给数字员工和自然人** | 中心分发任务 |
| **运维** | 部署、监控 | 闭环延伸到构建、签名、制品、发布 | 最后一层连接能力 |

> 人机混合编队：数字员工跑吞吐，自然人做判断。

## 五、常见 Q&A（售前/交付关键问题）

### 决策层

| 问题 | 腾讯回答 |
|------|---------|
| **ROI 怎么算？** | 积分制，按模型不同消耗不同倍率，腾讯内部平均 1200 积分/席位/月 参考 |
| **与竞品差异？** | 腾讯背书 + 长期路线图 + 大客户案例 + 稳定国内外模型资源 |
| **内部怎么推广？** | 配置足量积分给用户体验，比"集成性强"更重要 |
| **代码会泄漏吗？** | 数据分片传给大模型，云端不存储用户代码 |

### 技术层

| 问题 | 腾讯回答 |
|------|---------|
| **历史项目如何接入？** | `codebuddy init` 快速接入，不建议拍脑袋说"工期缩短 X 倍" |
| **自动化测试怎么做？** | 研发端单元测试 → 测试团队自动化测试 → AI 生成测试用例 |
| **模型怎么选？** | 海外模型（方案设计）+ 国产模型（执行），数据不出海 |
| **团队经验怎么沉淀？** | 通过 `MCP` 插件接入知识库，团队规则用 `CLAUDE.md` / `AGENTS.md` |

## 六、落地路线图（23 条需求 + 21 份 KM，P0/P1/P2）

### P0（必须打基础）

- 统一上下文注入（架构红线、质量门禁、安全合规）
- 规约分层治理，组织级宪章 → 项目级继承
- 工作环境配置标准化

### P1（规模化扩展）

- 六工种能力上线
- Monorepo vs Multirepo 决策（不允许一刀切）
- 设计稿到代码：Figma → Code、腾讯设计协同平台

### P2（持续优化）

- 自动化 CD 管道（构建→签名→制品→发布）
- 配置定期复盘（每季度审查、每次模型升级后重评）
- 组织级知识沉淀制度化

---

## 七、安全与治理

| 层级 | 方法 |
|------|------|
| **数据安全** | 数据分片传模型、云端不存储、高密级用海外模型做设计 + 国产模型做执行 |
| **组织级宪章** | 安全红线、架构红线、质量门禁先定边界 |
| **规约分层** | 组织级 → 项目级继承，每次变更带同一套约束 |
| **治理** | 至少一个明确负责人维护配置标准、权限策略与更新节奏 |

## 八、对个人职业发展的借鉴分析

> 用户背景：8 年新华三 PL + 工程化经验，嵌入式设备/RTOS/组网，正在学习端侧 AI（TFLM）。目标：转型端侧 AI 岗位。

### 8.1 直接可借鉴的（立即落地）

| 借鉴点 | 对你的价值 | 落地方式 |
|--------|----------|---------|
| **SDD 五步主链** | 你已有的 `brainstorming` + `writing-plans` Skills 就是这条链的核心 | ✅ ContextStack 已有，直接用 |
| **三层工具理解** | 你之前困惑的 SuperPowers vs SpecKit vs OpenSpec，现在彻底理清了 | ✅ 归档文档已写好（`sdd-tools-comparison.md`） |
| **六工种重组思路** | 你在 H3C 做过 PL，正是"需求→架构→研发→测试→交付"全链路，这套方法论对你面试时讲"工程化能力"极有价值 | 面试话术：**"我不是只会写代码，我做过全链路工程化"** |
| **历史项目接入** | 嵌入式项目不需要从零搭建 AI 流程，`codebuddy init` 即可快速接入 | TFLM 项目可以直接试 |
| **MCP 知识库** | 团队规则沉淀 → MCP 接入，对应你的"框架→技能→记忆"三层 | ContextStack 已经做到了 |

### 8.2 面试话术素材（关键词摘录）

```
"过去软件工程的稀缺资源是编码能力，AI 让代码、方案、测试样板快速产出后，
系统瓶颈从'能不能写出来'变成'能不能判断对'。
我的价值在于：8 年工程化经验，做的正是'定义边界、设计约束、
关键判断、高风险验证与失败复盘'——这正是 AI 时代最需要的人的能力。"
```

### 8.3 需要补齐的（与培训内容比对你的缺口）

| 缺口 | 培训要求 | 你现在 | 优先级 |
|------|---------|--------|:---:|
| **TDD** | 强制测试先行 | ❌ 未安装该 Skill | 🟡 可补 |
| **自动化测试** | AI 生成测试用例 | ❌ 嵌入式测试经验有但未体系化 | 🟢 加分项 |
| **组织宪章** | 架构红线、质量门禁、安全合规 | 🟡 ContextStack 有 GLOBAL-RULES 但缺嵌入式领域规约 | 🟡 面试可讲 |
| **CI/CD 管道** | 构建→签名→制品→发布 | 🟡 有 Git auto-push，缺完整管道 | 🟢 非刚需 |
| **设计稿驱动** | Figma → Code | ❌ 嵌入式中不适用 | — 不适用 |

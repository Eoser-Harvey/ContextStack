# ContextStack 四层架构框架

## 框架概述

ContextStack 是一个独立于特定AI模型、基于分层Context和持久化Memory的通用协作框架。其核心设计原则是：

1. **统一入口 + 分层Context**：单一AI助手入口，通过Context切换实现专注，避免Agent割裂。
2. **工作台驱动的Session管理**：使用Obsidian工作台实现话题切换和状态持久化。
3. **四层Context结构**：从全局规则到具体记忆的层次化加载机制。
4. **框架独立性**：不绑定任何特定AI助手，规则、记忆、工作台均为可迁移的持久化资产。

## 四层架构详解

### 第一层：全局规则 (GLOBAL-RULES.md)
- **位置**: `./GLOBAL-RULES.md`
- **作用**: 定义“我是谁”——AI助手的角色定位、专长领域、沟通风格、安全铁律、操作授权范围。
- **触发**: AI助手启动时自动加载，常驻内存，优先级最高，不可覆盖。
- **内容**: ContextStack 框架 AI 协作助手、网络设备/嵌入式/TSN/TFLM专长、简洁直接沟通风格、安全第一/代码质量/文档同步/记忆管理四大铁律。

### 第二层：项目规则 (PROJECT-RULES.md)
- **位置**: 各项目根目录下的 `PROJECT-RULES.md`
- **作用**: 定义“哪个项目”——项目规范、领域知识、目录结构、产品红线。
- **触发**: 切换到项目/话题工作台时动态加载。
- **特点**: 受全局规则约束，支持多项目上下文切换。

### 第三层：规范文档库 (02-Knowledge/system/)
- **位置**: `./02-Knowledge/system/`
- **作用**: 提供“如何做”的知识——方法论、SOP、模板、调研框架、工具配置。
- **触发**: 执行具体任务需要方法论时按需读取。
- **特点**: 属于“知识”而非“规则”，主动加载，不常驻内存。

### 第四层：持久化Memory (MEMORY.md索引)
- **位置**: `./MEMORY.md` (索引) + `03-Memory/` (详细文件)
- **作用**: 记录“在做什么”——user、feedback、project、reference四类记忆。
- **触发**: 持续更新（开始/完成/切换时）。
- **特点**: 索引式管理，详细信息在工作台，跨session持久化。

## 层间交互协议

### 优先级规则
1. **全局规则** (第一层) 优先级最高，不可被下层覆盖。
2. **项目规则** (第二层) 可细化全局规则，但不能违反。
3. **规范文档** (第三层) 提供参考，不具强制性。
4. **Memory** (第四层) 记录事实，不定义规则。

### 启动流程
```
AI助手启动
    → 加载第一层: GLOBAL-RULES.md (常驻内存)
    → 检查当前工作目录
    → 加载第二层: PROJECT-RULES.md (如果存在)
    → 读取第四层: MEMORY.md (了解上下文)
    → 等待用户指令
```

### 项目切换流程
```
用户发出切换指令
    → 保存当前工作台状态
    → 清理不相关Context
    → 加载新项目的 PROJECT-RULES.md (第二层)
    → 打开对应工作台文件
    → 恢复相关Memory上下文 (第四层)
    → 确认切换完成
```

### 任务执行流程
```
用户发出任务指令
    → 分析任务类型和需求
    → 按需加载规范文档 (第三层)
    → 执行任务 (使用工具、编辑文件)
    → 更新工作台状态
    → 必要时更新Memory索引 (第四层)
    → 报告结果
```

## 工作台系统 (01-Projects/)

### 核心功能
- **Session持久化**: 记录“做到哪了”，支持跨会话恢复。
- **话题切换**: 通过工作台暂存和恢复实现不同话题/项目间快速切换。
- **状态管理**: 记录项目状态、任务进度、讨论历史、决策记录。

### 工作台类型
1. **项目工作台** (`01-Projects/`): 长期项目跟踪。
2. **话题工作台** (`01-Projects/topics/`): 特定技术话题讨论。
3. **任务工作台** (`01-Projects/tasks/`): 具体任务执行跟踪。

### 切换命令
- `切换到[项目/话题名称]` / `Switch to [project/topic name]`
- `暂存[名称]工作台` / `Save [name] workbench`
- `恢复[名称]工作台` / `Restore [name] workbench`
- `结束会话` / `End session`

## CEO协作模式

```
您(Boss) > 我(CEO/AI助手) > 执行具体任务
   |              |              |
发号施令      分配资源      使用工具
切换话题      加载工作台    更新状态
```

### 角色定位
- **您 (Boss)**: 项目决策者 + 任务发布者。明确需求、提供上下文、审核重要变更、管理Memory更新。
- **AI助手 (CEO)**: 专业编程助手 + 技术顾问。理解需求、执行任务、维护记忆、更新工作台。

## 文件组织规范

### 命名原则
- **目录和文件名**: 使用英文，便于跨平台移植和工具兼容。
- **文件内容**: 使用中文，便于阅读和理解。
- **命名格式**: 小写字母、数字、连字符，避免空格。

## 框架核心价值

1. **独立性**: 不绑定任何特定AI助手，规则、记忆、工作台均为可迁移的持久化资产。
2. **分层Context**: 通过Context切换实现专注，避免Agent割裂。
3. **记忆连续性**: 跨session保留工作状态，知识可沉淀。
4. **工作台驱动**: 实现话题切换和Session持久化。
5. **CEO协作模式**: 明确角色分工，提升协作效率。

### 示例：自研RTOS

**问："你做过RTOS开发？"**

| 普通回答 | 工程叙事 |
|---------|---------|
| "做过，自己写过一个RTOS，有任务调度、信号量、中断管理" | 「RTOS本质是资源受限场景下的确定性调度。我在爱博精电时从头写过一个，跨了ARM M4和DSP两个平台：ARM版内核~5KB、每任务仅256B栈（TCB静态预分配），DSP版内核~10KB、支持Mutex/Flag/Alarm，每任务TCB 36B+栈800B。

踩过最深的坑是优先级反转——但不是教科书里那种经典的三任务反转。实际场景更隐蔽：

系统里有三个任务：
高优先级的测量计算任务（Prio 5）——DMA 在后台自动把 SPI 的 ADC 采样数据搬到内存（零 CPU 开销），DMA 完成中断发信号量唤醒此任务，负责计算有效值、功率等并更新共享结构体；
中优先级的通信任务（Prio 3）——Modbus 从机通信，UART 收到完整请求帧后事件触发：CRC 校验、解析功能码、打包应答数据并填充发送缓冲区，约 80ms 纯计算，期间**没有任何阻塞调用**（无 Delay、无 SemWait、无 QueueRecv）；
低优先级的 LCD 刷新任务（Prio 1）。

它们共享一个互斥锁保护的测量结果结构体。问题触发链路：

LCD 任务先拿到互斥锁（正在遍历结构体读取显示数据）→计算任务被 DMA 完成中断唤醒，抢先 LCD 执行，试着拿互斥锁来更新新计算结果→发现被 LCD 持有，挂起等待 LCD 释放。**这里有两个关键机制**：(1) 互斥锁不看优先级——谁先拿到谁持有，后来的不管优先级多高都得排队等。所以计算任务虽然优先级最高，调了 MutexLock 发现锁被占，RTOS 直接把它置为阻塞态，挂在互斥锁的等待链表上。(2) 计算任务一旦阻塞，就退出了 CPU 竞争——调度器只在就绪任务中选最高优先级，阻塞态的任务不在候选池中。此时 LCD 是唯一就绪的低优先级任务，调度器理应让它运行以释放锁。但通信任务恰好在这时被缓冲区满事件唤醒——它优先级比 LCD 高（3 > 1），且 80ms 的处理全程是纯计算，没有任何阻塞点让出 CPU。LCD 虽然持有锁，但这 80ms 内完全得不到 CPU 去执行 MutexUnlock()。锁释放不了，计算任务永久挂起。

结果就是计算任务超时——测量结果长时间不更新，设备失去实时响应能力，最终触发安全复位。

> 注：真实系统不止 3 个任务（Idle、定时器、日志等都在），但优先级反转只涉及「锁依赖链上的任务」。Idle(0) 低于 LCD(1) 轮不到 CPU；更高优先级任务（≥4）虽然会打断 Comm(3)，但它们不持有那个互斥锁，运行完就让出 CPU，锁仍然在 LCD 手里——锁的释放没人代理。

**为什么通信任务不退出就绪态？** RTOS 里任务只有两种方式让出 CPU：①主动调阻塞函数（SemWait/QueueRecv/Delay）→变为阻塞态；②被更高优先级任务抢占→回到就绪态。通信任务的 80ms 处理全是纯计算（打包帧+CRC+填缓冲区），没有任何阻塞调用，因此不会主动让出 CPU。同时没有比它更高优先级的就绪任务抢占它（计算任务阻塞在锁上，不在就绪队列）。所以就绪→运行→就绪→运行的循环中，通信任务一直占着 CPU，80ms 内 LCD 完全没有执行机会。

**80ms 为什么触发安全复位？** 看门狗不是直接监控计算任务——它监控主循环心跳。但计算任务被死锁后，测量结果永远是旧数据，下游保护逻辑（继电器/告警模块）读到连续多帧未更新的异常状态，判定数据流已断裂，触发安全复位。50Hz 系统中 80ms = 错过 4 帧数据，系统安全策略不容许这个级别的失能。

修复分两步：短期在规范里禁了锁内调任何可能导致阻塞的函数（SemWait/QueueRecv/延时），长期给互斥锁加了优先级继承——锁持有者自动继承等待者的最高优先级。后面再没出过类似问题。

**FreeRTOS**

**堆栈分配**
避免堆栈溢出：使用 uxTaskGetStackHighWaterMark()（FreeRTOS）或堆栈检测钩子函数。
典型需求：任务栈深 512B~4KB（根据局部变量、函数调用深度调整）。

**优先级反转预防**
使用优先级继承互斥锁（如 xSemaphoreCreateMutex()）替代二值信号量。
一句话：把"谁在等锁"的最高优先级临时借给"谁拿着锁"，让锁持有者能跑完临界区。

**中断设计**
ISR原则：快进快出，通过任务通知（Task Notification）或队列传递数据到任务。
```
// FreeRTOS中断中发送通知
void IRQ_Handler() {
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    vTaskNotifyGiveFromISR(xTaskHandle, &xHigherPriorityTaskWoken);
    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}
```

**低功耗模式**：利用IDLE任务钩子函数进入睡眠：
```
void vApplicationIdleHook(void) {
    __WFI(); // ARM Cortex-M睡眠指令
}
```
L1 硬件层：MCU 睡眠模式分级
| 模式                | 功耗               | 唤醒源               | 唤醒后               |
|:--------------------|:-------------------|:---------------------|:---------------------|
| **Run**             | 全速               | —                    | —                    |
| **Sleep**（`__WFI`）| CPU 停，外设跑      | 任意中断              | 立即恢复，PC 继续     |

**RTOS核心机制理解**

任务调度：解释基于优先级的抢占式调度。重点：优先级反转问题及解决方案（优先级继承、优先级天花板）。

| 维度              | 优先级继承                                       | 优先级天花板                                     |
|:------------------|:------------------------------------------------|:------------------------------------------------|
| **触发时机**       | 被动——高优先级任务阻塞等锁时，才临时提升锁持有者     | 主动——任务拿到锁的瞬间，立即提升到天花板优先级      |
| **提升到多高**     | 所有等待者的最高优先级                             | 创建锁时固定的天花板值（所有可能访问该锁的任务中最高优先级）|
| **开销**           | 按需触发，无争用零开销                             | 每次拿锁都提升，即使没争用                         |
| **死锁**           | ❌ 不能避免（A等B的锁，B等A的锁）                   | ✅ 能避免——同一天花板优先级任务不会同时持有锁        |
| **实现复杂度**     | 需要维护等待队列，遍历找最高优先级                  | 不需要等待队列，取锁时直接改优先级                   |
| **适用场景**       | 通用场景（FreeRTOS、Linux内核）                    | 硬实时系统（航空/医疗），对确定性要求极高            |

简单对比：
- 继承 = "谁在等我？把它的优先级借我用一下"
- 天花板 = "这锁可能被大佬用，我拿到就先按大佬的级别跑"

内存管理：静态内存池 vs 动态堆分配。在RTOS中强烈推荐使用静态内存池，因为分配时间确定，无碎片，适合实时系统。

任务间通信：
- 队列：用于传递数据，通常FIFO，可实现任务同步。
- 信号量：用于资源计数和任务同步。二进制信号量常用于互斥访问（但有优先级反转风险），互斥锁是解决互斥访问的更好选择（通常实现了优先级继承）。
- 事件组：用于多事件同步，一个任务可以等待多个事件的任意组合。

**面试问答：FreeRTOS调度算法**

Q: FreeRTOS的任务调度算法是什么？优先级抢占机制的核心是什么？如何保证嵌入式系统的1ms级实时响应？

① 核心调度算法：FreeRTOS采用"基于优先级的可抢占式调度算法"，同时支持时间片轮转调度（同优先级任务）；高优先级任务就绪时，会立即抢占低优先级任务的CPU使用权，低优先级任务只能在高优先级任务阻塞（如延时、等待信号量）时运行。

② 优先级抢占机制核心：任务控制块（TCB）中存储任务优先级，系统维护一个优先级位图（uxTopReadyPriority），快速定位当前最高优先级的就绪任务；调度器在任务阻塞、中断退出、任务创建/删除时，触发任务切换，确保高优先级任务优先执行。

③ 保证1ms级实时响应（结合西门子楼宇/消防场景）：
a. 合理分配任务优先级，将核心实时任务（如消防报警信号处理、电机闭环控制）设置为高优先级，后台任务（如日志打印、参数保存）设置为低优先级；
b. 优化中断处理函数，缩短中断执行时间，避免在中断中做耗时操作（如printf打印），耗时操作通过信号量交给后台任务处理；
c. 关闭不必要的中断，减少中断嵌套层数，避免优先级反转；
d. 优化任务切换时间，合理配置FreeRTOS的系统时钟节拍（tick），一般设置为1ms，同时禁用不必要的任务切换钩子函数；

**面试问答：优先级反转**

Q: FreeRTOS中，任务优先级反转是什么？如何解决？请结合工业场景举例。

① 优先级反转定义：高优先级任务等待低优先级任务释放资源（如信号量、互斥锁），而低优先级任务又被中优先级任务抢占，导致高优先级任务无法及时执行，出现"优先级倒置"的现象，影响系统实时性。

② 解决方法（3种，重点讲工业场景常用的2种）：
a. 优先级继承机制：当低优先级任务持有高优先级任务需要的互斥锁时，暂时将低优先级任务的优先级提升到与高优先级任务相同，直到低优先级任务释放互斥锁，再恢复其原优先级（FreeRTOS的xSemaphoreCreateMutex()创建的互斥锁，默认支持优先级继承）；
b. 优先级天花板机制：将持有资源（互斥锁）的所有任务，优先级提升到所有可能申请该资源的任务中的最高优先级，避免低优先级任务被中优先级任务抢占；

举例（贴合8年经验+西门子场景）：我之前开发消防报警系统，高优先级的"报警信号处理任务"需要等待低优先级的"数据存储任务"释放Flash资源，而中优先级的"传感器数据采集任务"会抢占低优先级任务，导致报警信号延迟处理（最长达3ms，超出国标要求）。后续采用优先级继承机制，当低优先级任务持有Flash资源时，自动提升其优先级，解决了优先级反转，将报警响应延迟控制在0.5ms以内，符合消防系统国标要求。

>> 内核支持优先级继承(内核自动调节性能会好一些) 1）用了内核级的优先级继承机制（Mutex），而不是应用层手动提权  2）必须用互斥锁（Mutex），不能是信号量（Semaphore），信号量不支持优先级继承
>> 最经典案例是火星探路者号任务失败事件——当时就是因为没有处理优先级反转。

**RTOS 内核类型与实时系统基础**

不可剥夺型内核（Non-Preemptive Kernel）:
1. 不可剥夺型内核要求每个任务自我放弃CPU 的所有权；
2. 某任务主动放弃CPU 的使用权时，那个高优先级的任务才能获得CPU的使用权；
3. 异步事件还是由中断服务来处理。中断服务可以使一个高优先级的任务由挂起状态变为就绪状态。但中断服务以后控制权还是回到原来被中断了的那个任务；
不可剥夺型内核的另一个优点是，几乎不需要使用信号量保护共享数据。

可剥夺型内核：
1. 当系统响应时间很重要时，要使用可剥夺型内核；
2. 使用可剥夺型内核时，应用程序不应直接使用不可重入型函数；

实时系统大多综合了软实时和硬实时：
1. 软实时系统只是要求任务执行得尽量快，并不要求在某一特定时间内完成。硬实时系统中，任务不但要执行无误，还要准时完成。
2. 优先级分配方法一：哪个任务执行的次数最频繁,执行最频繁的任务优先级最高，但是实际应用执行次数多的任务，不一定是重要的任务，所以实际应用需要根据具体情况再定；

**问答：Systick 与 PendSV 中断优先级设计**

Q1: FreeRTOS 为什么用 PendSV 做上下文切换，而不是直接在 Systick 里切？

Systick 负责"通知"，PendSV 负责"执行"。PendSV 优先级设为最低，确保所有 ISR 执行完后再切换，不会在中断处理中途抢占。Systick 中断里只触发 PendSV 异常登记（`portNVIC_INT_CTRL_REG = portNVIC_PENDSVSET_BIT`），等 CPU 退出所有 ISR 后，PendSV 才执行真正的上下文切换。一句话总结：**「Systick 负责通知，PendSV 负责执行，保证上下文切换发生在所有中断处理完成之后。」**

> 🔍 追问：PendSV 上下文切换过程中被高优先级中断打断怎么办？

**可以被打断，而且这正是刻意设计的。** 流程如下：

| 阶段 | 发生了什么 |
|:-----|:-----------|
| PendSV 正在保存当前任务上下文 | 高优先级中断来了 → NVIC 立即抢占 PendSV |
| ISR 执行（如串口收到数据） | ISR 调用 `xSemaphoreGiveFromISR()`，唤醒了一个更高优先级的任务 |
| ISR 退出 | NVIC 回到 PendSV 继续执行 |
| PendSV 恢复执行 | 重新调用 `vTaskSwitchContext()`，选 ISR 唤醒的那个更高优先级任务 |

**为什么不会乱？** Cortex-M 的双栈机制保证安全：PendSV 用 PSP（进程栈）保存任务寄存器，ISR 用 MSP（主栈），两个栈物理分离，ISR 的压栈不会破坏 PendSV 正在保存的任务上下文。PendSV 恢复后从 PSP 指向的位置继续干活，毫发无损。

> 一句话：**「PendSV 优先级最低是刻意为之——宁可上下文切换被打断，也不能让紧急硬件中断等。被打断后恢复时，重新评估最高优先级任务，不丢不重。」**

Q2: Systick 和 PendSV 的中断优先级怎么配？为什么？

| 异常 | 优先级 | 原因 |
|:-----|:-------|:-----|
| Systick | 最低（通常 15，`configKERNEL_INTERRUPT_PRIORITY = 255`） | 不能让 OS 时钟中断抢占硬件 ISR（如串口、定时器） |
| PendSV | 最低（通常 15，与 Systick 同级） | 确保在所有 ISR 执行完毕后、回到线程模式前，才执行上下文切换 |

如果 Systick 优先级高于外设 ISR，外设数据可能丢失。Cortex-M 中 `configKERNEL_INTERRUPT_PRIORITY` 通常设为 `255`（最低），所有不调用 FreeRTOS API 的 ISR 优先级可以设得更高，不受限制。

Q3: `configMAX_SYSCALL_INTERRUPT_PRIORITY` 是什么？怎么用？

| 场景 | 优先级配置 |
|:-----|:-----------|
| 串口接收中断（需要 `xSemaphoreGiveFromISR` 等 API） | 优先级 ≥ configMAX_SYSCALL_INTERRUPT_PRIORITY |
| 纳秒级 GPIO 翻转（不需要 OS API） | 优先级可以高于该值，不受限制 |

核心原理：Cortex-M 用 `BASEPRI` 寄存器屏蔽低优先级中断。`configMAX_SYSCALL_INTERRUPT_PRIORITY` 以下的优先级被屏蔽，不能调用 FreeRTOS API，否则会破坏内核数据一致性。FreeRTOS 建议 `NVIC_PriorityGroupConfig(NVIC_PriorityGroup_4)`，全用抢占优先级，子优先级被忽略。

#### 🔧 RTOS 三大实战问题：原理 + 代码 + 案例（来自自研 AcuOS）

**一、任务栈溢出：如何发现和预防**

> 📌 你的代码中的实现（DSP版 `AcuOsCoreDsp.c` 第235-254行）

```
T_OsTcb 中有 uiStkFree 字段，初始为 uiStkSize（任务栈大小）。
每轮调度后调用 OsStkCheckClr() 遍历栈底部，统计连续的 0x00000000：
- 栈初始化时全部清零（g_auiTaskIdleStk = {0}）
- 运行时压栈会将对应地址写入非零值
- 统计连续零值字数量 = 栈剩余空间
- uiStkFree → 0 时说明栈即将溢出
```

**原理**：栈从高地址向低地址生长。如果 `uiStkFree` 趋近于 0，说明栈顶已经接近 TCB 结构体，下次函数调用可能覆写 TCB → 任务崩溃。

**案例**：DSP 做 1024 点 FFT 时，局部变量 `float fftBuf[1024]` 直接占满 800 字节栈（每个 float 4B × 1024 > 800B 栈空间），导致 `uiStkFree = 0`。解决：将大数组改为静态分配或从堆分配。

**面试话术**：
> 「我在 TCB 里维护了一个 `uiStkFree` 字段，每次调度结束后扫描栈底连续零值来估算剩余空间。实际踩过坑：DSP 上 FFT 任务在栈上开了个大数组，直接把栈打穿覆写了相邻 TCB，现象是任务莫名其妙跳到非法地址。后来规范了：所有 >256B 的局部数组一律静态分配。」

**对照：FreeRTOS 如何检测和预防栈溢出**

FreeRTOS 提供了两套方案，比 AcuOS 的"扫描零值"更完备：

| 方案 | 实现方式 | 优缺点 |
|------|------|------|
| **方案一：运行时检测** `configCHECK_FOR_STACK_OVERFLOW=2` | 任务切换时检查栈顶指针是否越界 + 检查栈底 canary 是否被破坏 | ✅ 实时检测，溢出立即触发 hook；❌ 只在切换时检查 |
| **方案二：水印检测** `uxTaskGetStackHighWaterMark()` | 栈初始化时全部填入 `0xA5`，运行时统计栈底连续 `0xA5` 个数 = 剩余空间 | ✅ 原理和 AcuOS 完全一样（只是填充值不同）；❌ 需主动调用 |
| **MPU 保护（Cortex-M 高级）** | 配置 MPU 在任务栈底放一个不可访问页，溢出时触发 MemManage Fault | ✅ 硬件级零开销；❌ 需要 MPU 支持，内存粒度对齐 |

**核心差异**：

```
FreeRTOS 栈初始化：全部填入 0xA5A5A5A5（已知魔数）
AcuOS   栈初始化：全部清零  0x00000000

检测逻辑完全相同：从栈底向上数，连续"初始值"的个数 = 剩余空间
```

**FreeRTOS 的"溢出直接挂钩"机制**（AcuOS 没有）：

```c
void vApplicationStackOverflowHook(TaskHandle_t xTask, char *pcTaskName) {
    // 栈真的溢出了！立即记录 + 安全重启
    // AcuOS 没有这个——只能靠 uiStkFree 趋近 0 时人工判断
}
```

**面试加分对比话术**：
> 「FreeRTOS 的栈检测比我的 AcuOS 多一层兜底——除了水印法，它还有 `configCHECK_FOR_STACK_OVERFLOW=2` 在每次任务切换时检查栈顶，加上溢出 hook 可以自动触发安全处理。不过核心原理一样：填初始值→运行后扫描剩余连续初始值→得到剩余空间。差别只是 FreeRTOS 用 `0xA5`、我用 `0x00`。」

**二、临界区关中断过长导致通信丢包**

> 📌 代码依据：`SharcDsp.c:58-90`（关/开中断实现）+ `AcuOsCoreDsp.c`（所有调用了 `OS_ENTER_CRITICAL` 的函数）

#### 场景还原：Modbus RTU 通信中突然丢包

**系统背景**：Acuvim 电力仪表通过 Modbus RTU（RS-485）和上位机通信。DSP 上同时跑 5 个任务 + 空闲任务，调度器 `OsTimeTick()` 每次中断都走一遍 `OsSchedule()`。

**故障现象**：上位机每 200ms 发一次 Modbus 读取命令，偶尔（约 2-5% 概率）无响应 → 超时。连续读 1000 次大概丢 20-50 次。但 ADC 采样、FFT 计算都没有异常——不是系统卡死，只是通信偶尔断。

#### 根源追踪（逐步骤还原）

```
时间轴（假设 OS Tick = 1ms，波特率 115200，每字节 ≈ 87μs）：

T=0.000ms  定时器 Tick 中断触发 → OsTimeTick() 进入
T=0.005ms  OsTimeTick() 第178行调用 OS_ENTER_CRITICAL()
           → SharcDsp.c:63: BIT CLR MODE1 0x1000
           【此时所有中断关闭，包括 UART 接收中断】

T=0.087ms  UART 收到 Modbus 第1个字节(地址码 0x01) → 触发 UART RX 中断
           → 中断被 BIT CLR MODE1 屏蔽 → ISR 不执行 → 字节暂存在 UART FIFO

T=0.174ms  UART 收到第2个字节(功能码 0x03) → 等待在 FIFO 队列

T=0.261ms  UART 收到第3个字节 → FIFO 第3个位置

...每 87μs 来一个字节...

T=0.783ms  UART 收到第9个字节 → FIFO 第9个位置

T=0.870ms  UART 收到第10个字节 → FIFO 第10个位置
           
T=1.000ms  OsSchedule() 执行中（遍历 TCB 链表选最高优先级就绪任务）
           假设有 7 个应用任务 + 3 个内部任务 = 10 个 TCB
           遍历一次约 30-50μs，但可能包含 OsPreSchedule() 的循环

T=1.050ms  OsSchedule() 结束 → 走 OsContextSwitchInt() → 任务切换

T=1.200ms  OS_EXIT_CRITICAL() → g_uiCpuSr 减到 0
           → sysreg_bit_set(IRPTEN) 【中断恢复！】
           
           此时 UART FIFO 中已经积压了 12-14 个字节。
           但 SHARC DSP 的 UART FIFO 深度只有 16 字节。
           
           Modbus RTU 一帧典型长度 ≈ 8-256 字节。
           如果这次关中断时间达到 1.5ms（17-18 个字节），
           FIFO 溢出 → 最早收到的字节被覆盖 → 帧不完整 → CRC 错 → 丢包！
```

#### 代码中真实的长临界区路径

搜索 `AcuOsCoreDsp.c` 中所有 `OS_ENTER_CRITICAL` 块，最耗时的是：

```
OsTimeTick() (第174行)      → 关中断 + 走 OsTickDlyCheck() + OsSchedule() → 约 0.3-1.2ms
OsQPost() (第381行)         → 关中断 + 遍历队列 + OsSchedule() → 约 0.05-0.3ms
OsQPend() (第416行)         → 同上
OsTaskCreate() (第256行)    → 关中断 + 链表插入 → 约 0.05ms
```

#### 后果量化

| 项目 | 正常 | 故障时 |
|------|:--:|:--:|
| 上位机读取 1000 次 | 0 次超时 | **20-50 次超时** |
| 丢包率 | 0% | 2-5% |
| 1小时连续运行 | 0 次异常 | 几百次 CRC 校验失败 |
| 根源 | — | 关中断时长 > UART FIFO 深度 |

#### 解决方法

```
① DMA + 空闲中断（根本解决）
   → UART 不靠 RX 中断逐字节收
   → 配置 DMA 自动搬运到环形缓冲区
   → 空闲中断触发时一次性处理整帧
   → 关中断期间 DMA 继续运行，不丢数据

② 硬件 FIFO 深度利用
   → SHARC DSP UART 可配置触发等级
   → 设置为 FIFO 过半触发中断（而非每字节触发）
   → 减少中断频率，同时缓冲更多字节
```

#### 面试话术

> 「电力仪表上 10ms ADC 采样和 200ms Modbus 通信并行跑。曾遇到一个诡异 bug：通信偶尔丢包 2-5%，但系统不卡死。定位方法是关掉所有用户任务只跑通信 → 正常；说明问题不在通信代码本身。然后逐个打开任务，发现加到 5 个以上任务后丢包率上升——原来 `OsTimeTick()` 关中断长达 1.2ms，而 UART FIFO 只有 16 字节深度，115200 波特率下 1.4ms 就溢出了。解决：把 OsSchedule() 里不依赖原子保护的逻辑移到临界区外，关中断时长降到 0.2ms，丢包消失。更根本的解法是 DMA+空闲中断接收，关中断期间 DMA 照跑不误。」

#### 🔍 深入：OsExitCritical 嵌套计数机制详解

> 📌 代码依据：`SharcDsp.c:58-90`，完整实现仅 33 行

```
Uint32 OsEnterCritical(void) {
    uiMask = sysreg_bit_tst(sysreg_MODE1, IRPTEN);   // ①先读当前中断状态(开/关)
    BIT CLR MODE1 0x1000;                             // ②汇编: 关中断
    g_uiCpuSr++;                                      // ③全局嵌套计数+1
    if (g_uiCpuSr == 1)                               // ④只有最外层才保存原始状态
        g_uiSavedIntMask = uiMask;
    return (g_uiCpuSr);                               // ⑤返回当前计数
}

void OsExitCritical(Uint32 uiCpuSr) {
    g_uiCpuSr = uiCpuSr;     // ①恢复到"我进入时"的计数值
    g_uiCpuSr--;              // ②我这层退出，减1
    if (g_uiCpuSr == 0) {     // ③所有层都退出了？
        if (0u != g_uiSavedIntMask)
            sysreg_bit_set(IRPTEN);  // ④恢复中断
    }
}
```

**单层调用**（99%的场景）：

```
OS_ENTER:  g_uiCpuSr: 0 → 1 → return 1
           g_uiCpuSr==1 → 保存中断状态 → 关中断
           
OS_EXIT:   uiCpuSr=1 → g_uiCpuSr=1 → -1 → =0
           0==0 → 开中断 ✓
```

**嵌套调用**（func_A 关中断后又调 func_B）：

```
func_A::ENTER:  g_uiCpuSr: 0→1, CpuSr_A=1, 关中断
    │
  func_B::ENTER: g_uiCpuSr: 1→2, CpuSr_B=2
  func_B::EXIT:  g_uiCpuSr=2→-1→=1  (1≠0, 不开中断！)
    │
func_A::EXIT:    g_uiCpuSr=1→-1→=0  (0==0, 开中断！)
```

**核心设计哲学**：
- `g_uiCpuSr` = 当前还在临界区内的层数（0 = 完全退出）
- `uiCpuSr`（参数）= 快照值——"我进来时已经叠了几层"
- 退出时恢复快照再减 1 = 精确还原嵌套深度
- 只有深度归零（最外层退出）才真正开中断
- 如果进入时中断本来就是关的（`g_uiSavedIntMask == 0`），退出时也不开，保持原始状态

**三、DSP ↔ ARM M4 移植踩坑**

> 📌 两个平台的上下文切换实现差异

| | ARM Cortex-M4 | SHARC DSP |
|------|------|------|
| 切换触发 | PendSV 异常（最低优先级） | 自定义软件中断 |
| 寄存器保存 | **硬件自动**保存 xPSR/PC/LR/R12/R3-R0（8个） | **全部手动**保存（包括 DAG/SIMD） |
| 栈帧方向 | 满递减（先减 SP 再存） | 架构相关 |
| 临界区 | `__disable_irq()` / `__enable_irq()` | `BIT CLR/SET MODE1` |

**坑 1：PendSV 到自定义中断转换**

ARM 上 PendSV 是硬件自动压栈 8 个寄存器 + 手动压 R11-R4（8个）= 16 个寄存器。DSP 上需要手动保存所有通用寄存器 + DAG 寄存器 + SIMD 乘加器。移植时最容易遗漏的是 DAG 寄存器（地址生成器），因为 ARM 没有这个概念。

**坑 2：栈帧布局**

ARM 栈帧结构：`[R4, R5, ..., R11, (hardware) R0, R1, R2, R3, R12, LR, PC, xPSR]`

DSP 栈帧结构需要自己定义顺序，如果顺序不一致 → 恢复时寄存器错位 → 直接跑飞。

**坑 3：临界区嵌套**

ARM 上 `__disable_irq()` 是简单关中断。DSP 上你的实现加了 `g_uiCpuSr` 嵌套计数器（`SharcDsp.c:67`）——如果移植时忘了这个嵌套逻辑，多层临界区嵌套时提前开中断 → 数据竞争。

**面试话术**：
> 「跨平台移植改了三个地方：上下文切换入口（PendSV → 自定义中断）、栈帧布局（ARM 硬件帮你压 8 个，DSP 全手动）、临界区实现（DSP 加了嵌套计数器，ARM 直接 `__disable_irq`）。最坑的是 DAG 寄存器——ARM 没这东西，DSP 不保存的话任务切换回来地址生成全乱了。但调度核心代码一行没改，这就是分层设计的好处。」

### 示例：MQTT 协议 — 电力仪表数据上云

**问："你用过 MQTT 吗？具体怎么用的？"**

**问题本质**：MQTT 是物联网场景下设备与云端通信的事实标准，核心是发布/订阅模型，解决的是资源受限设备在不可靠网络下的可靠数据传输问题。

**项目背景**：爱博精电 Acuvim 系列电力仪表，现场测量电压、电流、功率、功率因数、谐波等电力参数，需要实时上报到公司云平台做能耗监控和配电运维。仪表端是 ARM Cortex-M4 + DSP 双核架构，M4 负责通信和人机交互，DSP 负责采样计算。

**我的角色**：负责设备端 MQTT 客户端的集成和调试。云端平台由后端团队开发，我负责把仪表测量数据按照约定的 Topic 和数据格式推上去，保证数据不丢、不断、不乱序。

**技术方案**：

| 维度 | 选型 | 理由 |
|:-----|:-----|:-----|
| MQTT 库 | Eclipse Paho MQTT C 嵌入式版 | 开源成熟、纯 C、RAM 占用 ~4KB，适合 MCU |
| 传输层 | TCP + TLS（可选） | 工业场景要求加密，非加密时用裸 TCP |
| QoS 策略 | 测量数据 QoS 1，告警数据 QoS 1 + Retain，配置下发 QoS 2 | 测量数据丢了无所谓下一帧补上，告警必须送达，配置不能重复执行 |
| Topic 设计 | `devices/{device_id}/telemetry`（上报）、`devices/{device_id}/command`（下发）、`devices/{device_id}/status`（在线状态） | 层级化，云端可用通配符 `devices/+/telemetry` 批量订阅 |
| 数据格式 | JSON（开发期）/ Protobuf（量产后） | JSON 调试方便，Protobuf 体积小 60%+，适合带宽受限场景 |
| 心跳机制 | KeepAlive = 60s | 仪表环境网络稳定，60s 够用；移动端设备建议 15-30s |

> 🔍 追问：为什么选 Paho 而不是 MQTT-C？

| 维度 | Eclipse Paho MQTT C | MQTT-C (Liam Bindle) |
|:-----|:--------------------|:---------------------|
| ROM 占用 | ~30KB | ~10KB |
| RAM 占用 | ~4KB | ~1KB |
| MQTT 版本 | 3.1.1 + 5.0 | 仅 3.1.1 |
| API 模型 | 同步 + 异步（非阻塞） | 仅同步（阻塞） |
| TLS 支持 | 内置（OpenSSL/mbedTLS 适配层） | 无，需自己在 socket 层包 |
| OS 依赖 | 需要 OS 抽象层（线程/互斥锁/信号量） | 零依赖，只需提供 `send/recv` 函数 |
| 断线重连 | 内置自动重连机制 | 需自己实现 |
| 社区维护 | Eclipse 官方项目，企业级 | 个人项目，社区较小 |

**选 Paho 的 4 个关键理由**：

1. **异步 API 不阻塞测量任务** — Paho 的 `MQTTClient_publish()` 立即返回，后台线程发 ACK；MQTT-C 的 `mqtt_publish()` 阻塞等 ACK，网络抖动超时（默认 15s）会拖死测量任务。电力仪表采样优先级最高，不能因为通信阻塞采样。
2. **内置 TLS** — 工业现场要求加密，Paho 对接 mbedTLS 几行代码搞定；MQTT-C 需自己在 socket 层包 TLS，工作量大且过安全认证时审查成本高。
3. **内置自动重连** — Paho 配置后断线自动重连；MQTT-C 需自己写重连状态机（~200-300 行）。
4. **RAM 不是瓶颈** — 64KB RAM 下 Paho 的 4KB 不构成约束。AcuOS ~8KB + LWIP ~16KB + Paho ~4KB + 测量缓冲 ~20KB = 48KB，剩余 16KB 可用。

**什么时候该选 MQTT-C**：RAM < 16KB（如 STM32F103）、裸机无 RTOS、不需要 TLS、极简单传感器上报场景。

**Topic 设计示例**：

```
# 设备上报测量数据（每 3 秒一次）
Topic: devices/ACUVIM_001/telemetry
Payload: {"ts":1719504000,"U":220.3,"I":5.6,"P":1234.5,"PF":0.98,"freq":50.01}

# 设备上报告警（事件触发）
Topic: devices/ACUVIM_001/alarm
Payload: {"ts":1719504005,"code":"OVER_VOLTAGE","level":"warning","value":253.2}

# 云端下发控制指令
Topic: devices/ACUVIM_001/command
Payload: {"cmd":"set_threshold","param":"over_voltage","value":250.0}

# 设备遗嘱消息（异常掉线时 Broker 自动发布）
Topic: devices/ACUVIM_001/status
Payload: {"online":false,"reason":"unexpected_disconnect"}
```

**踩过的坑**：

**坑 1：断线重连风暴**

现象：现场有 200 台仪表同时部署，网络抖动恢复后所有设备同时重连，Broker 瞬间连接数飙升导致拒绝服务。

原因：重连策略是固定 3 秒重试，没有退避机制。200 台设备同时 3 秒重试 = 同时涌入。

修复：改成**指数退避 + 随机抖动**：
```
base_delay = 1s
max_delay = 60s
retry_count = 0

delay = min(base_delay * 2^retry_count, max_delay) + random(0, 1s)
// 第1次：1-2s，第2次：2-3s，第3次：4-5s ... 第6次以后：60-61s
```

加随机抖动是关键——避免多台设备退避后仍然同步重连。

**坑 2：QoS 1 消息重复**

现象：云端收到重复的测量数据，数据库里同一条记录出现两次。

原因：QoS 1 保证「至少一次」，网络抖动时 Publish 的 ACK 丢了，设备端重发 → 云端收到两份。这是协议特性，不是 bug。

修复：设备端每条消息带唯一 `msg_id`（时间戳 + 序列号），云端做幂等去重：
```json
{"msg_id":"1719504000_00127","ts":1719504000,"U":220.3,...}
```
云端收到后先查 `msg_id` 是否已入库，已入库则丢弃。QoS 2 也能解决但握手开销太大（4 次交互 vs QoS 1 的 2 次），测量数据 3 秒一帧，不值得。

**坑 3：内存约束下的发送缓冲**

现象：Paho MQTT 默认发送缓冲区 1024 字节，但谐波数据（63 次谐波 × 3 相 × JSON 格式）超过 2KB，直接截断丢数据。

原因：MCU 的 RAM 只有 64KB，不能无脑加大缓冲区。

修复：**分帧上报**。把谐波数据拆成 3 帧（每相一帧），每帧 ~700 字节。同时把 JSON 换成 Protobuf，单帧从 700 字节压到 ~280 字节，一次就能传完三相。

| 方案 | 单帧大小 | 帧数 | 总耗时 | RAM 占用 |
|:-----|:---------|:-----|:-------|:---------|
| JSON 整包 | 2.1KB | 1 | 80ms | 4KB（改大缓冲区） |
| JSON 分帧 | 700B | 3 | 240ms | 1KB（默认缓冲区） |
| Protobuf 整包 | 280B | 1 | 30ms | 1KB |

最终选 Protobuf，单帧传完、耗时最短、内存没涨。

**坑 4：遗嘱消息没生效**

现象：设备拔网线后，云端迟迟不收到掉线通知，过了 5 分钟才触发。

原因：KeepAlive 设了 60 秒，但 Broker 的遗嘱触发逻辑是 `1.5 × KeepAlive = 90 秒`。加上网络层 TCP 的 keepalive 探测超时（默认 2 小时），实际感知时间更长。

修复：调整 KeepAlive 为 30 秒（ Broker 45 秒内判定掉线），同时在设备端加了**应用层心跳**：每 10 秒发一个空 Publish 到 status topic，云端 30 秒没收到就主动判定离线。两层心跳：MQTT KeepAlive 管 TCP 连接，应用心跳管业务可用性。

**核心数据**：
- 设备部署量：200+ 台仪表
- 上报频率：测量数据 3s/帧，告警事件触发
- 单帧大小：Protobuf ~280 字节
- 日均消息量：~580 万条（200 台 × 28800 帧/天）
- 断线重连成功率：99.7%（指数退避后）
- 数据丢失率：< 0.01%（QoS 1 + 幂等去重后）

**面试话术**：
> 「电力仪表场景下用 MQTT 做数据上云，设备端用 Paho MQTT 的 C 库集成到 ARM M4 上。核心设计是 QoS 分级——测量数据 QoS 1 够用丢了下一帧补，告警数据 QoS 1 + Retain 保证离线设备上线后也能收到。踩过断线重连风暴的坑，200 台设备同时重连把 Broker 打爆，改成指数退避 + 随机抖动解决。内存约束下把 JSON 换成 Protobuf，单帧从 2KB 压到 280B，一帧传完三相谐波数据。最容易被忽略的是遗嘱消息的触发时机——KeepAlive 60 秒意味着最差 90 秒才感知掉线，工业场景不能接受，加了应用层 10 秒心跳兜底。」

**面试追问预判**：

| 追问 | 回答要点 |
|:-----|:---------|
| 为什么不用 HTTP？ | HTTP 是请求/响应模型，设备需要主动拉取指令，不能做实时推送；MQTT 长连接 + 发布订阅，云端随时下发、设备随时上报，协议头才 2 字节 |
| 为什么不用 CoAP？ | CoAP 是 UDP 协议，工业现场网络质量不稳定，UDP 丢包率高；MQTT 基于 TCP，配合 QoS 1/2 能保证可靠性 |
| QoS 2 为什么不用？ | QoS 2 要 4 次交互（PUBLISH + PUBREC + PUBREL + PUBCOMP），3 秒一帧的测量数据用 QoS 2 带宽浪费 100%；只有配置下发这种「不能重复执行」的指令才用 QoS 2 |
| Broker 挂了怎么办？ | 设备端做了本地缓存——Broker 断连期间数据写入 SPI Flash 环形缓冲区（保留最近 24 小时），重连后按序补传；云端做主备 Broker + 负载均衡 |
| TLS 加密性能影响？ | TLS 握手增加 ~300ms 首次连接延迟，连接建立后对称加密开销 < 1ms/帧；MCU 用硬件加密加速器（如 STM32 的 CRYP 外设），CPU 占用增加 < 2% |
| 怎么保证数据安全（防篡改）？ | TLS 管传输层安全；业务层加 HMAC 签名，Payload 里带 `sign = HMAC-SHA256(device_secret, msg_id + ts + data)`，云端验签不通过则丢弃 |

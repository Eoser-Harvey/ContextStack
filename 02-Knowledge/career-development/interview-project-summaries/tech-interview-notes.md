## 一、RTOS 核心（最高频考点）

### 1.1 自研 RTOS (AcuOS) 性能数据

| 指标 | AcuOS (M4) | AcuOS (DSP) | FreeRTOS (参考) |
|------|-----------|------------|--------------|
| 内核 ROM | ~5KB | ~10KB | ~6-10KB |
| 静态 RAM（零任务） | ~1.3KB | ~2.6KB | ~2-3KB |
| TCB 大小 | 24 bytes | 36 bytes | ~56 bytes |
| 每任务栈（默认） | 256B (64 words) | 800B (200 words) | 可配 |
| TCB 分配方式 | 静态数组预分配 768B | 动态 | 动态/静态可选 |
| 32任务额外 RAM | ~8KB（栈256B×32）| ~25.6KB（栈800B×32）| ≥17KB |
| IPC 支持 | Semaphore + Queue | Semaphore + Queue + Mutex + Flag + Alarm | 全量 IPC |
| 上下文切换 | PendSV（标准 Cortex-M） | DSP 汇编 | PendSV |

**已支持特性**：任务创建/优先级/栈配置(静态)、信号量、消息队列、软件定时器、互斥锁、系统时间、系统负载率

**新增特性**：标志服务(Flag)、闹钟(Alarm)

### 1.2 AMP 多核架构（SC573 实战）

```
A5(Linux) ── DSP1(RTOS) ── DSP2(裸机)
                │
        高速ADC+DMA采样 = 10ms
        5个应用任务 + 空闲任务：
          任务1: 10ms/20ms 高实时数据搬运+FFT
          任务2: 200ms 插值+谐波计算
          任务3: 3s 谐波
          任务4: 告警
          任务5: A5↔DSP双核通信(200ms周期)
        协处理器DSP2: 闪变/频率计算(裸机)
```

**同步机制分布**：
- `OsQPend` 队列：DI采集、EEPROM写入缓冲
- `OsFlagPend` 标志：按键处理、Modbus通信
- `T_OsMutex` 互斥锁：EEPROM写锁、IIC总线锁
- `T_OsSem` 信号量：EEPROM写、软件缓存

### 1.3 任务调度

**FreeRTOS 调度算法**：基于优先级的可抢占式调度 + 同优先级时间片轮转

**优先级抢占核心**：
- TCB 存储任务优先级
- 优先级位图 `uxTopReadyPriority` 快速定位最高就绪任务（O(1) 时间复杂度）
- 自研RTOS使用16-bit位图 + `__clz` 指令实现O(1)
- 触发切换时机：任务阻塞/中断退出/任务创建删除

**保证1ms级实时响应**：
- 核心实时任务设为高优先级
- 中断处理函数短小精悍（耗时操作通过信号量交后台任务）
- 减少不必要中断嵌套
- tick一般设为1ms，禁用不必要的钩子函数

**不可剥夺型 vs 可剥夺型内核**：
- 不可剥夺：任务必须主动放弃CPU → 几乎不需要信号量保护共享数据
- 可剥夺：高优先级任务可抢占 → 不能使用不可重入函数

### 1.4 优先级反转

**定义**：高优先级任务等待低优先级资源 → 低优先级被中优先级抢占 → 高优先级被无限期阻塞

**解决方案（3种）**：
1. **优先级继承**：低优先级持有锁时临时提升到等待者最高优先级，释放后恢复（FreeRTOS `xSemaphoreCreateMutex()` 默认支持）
2. **优先级天花板**：持有资源的任务提升到所有可能申请者的最高优先级
3. **编码规范规避**：缩短临界区/限制访问者/统一优先级/避免嵌套锁/中断下半部

**经典案例**：火星探路者号任务失败 ← 优先级反转未处理

**实战案例**（消防报警系统）：
- 高优先级报警任务等待低优先级存储任务释放Flash → 被中优先级传感器采集任务抢占
- 报警延迟最长达3ms（超出国标）
- 采用优先级继承后，延迟控制在0.5ms内

**链式反转问题**：多个任务各自持有不同资源互相等待 → 编码规范禁止锁内调用可能引发等待的函数

### 1.5 Tickless 低功耗机制

**五步流程**：
1. 空闲检测 → 2. 计算休眠时长 → 3. 配置LPTIM → 4. 进入休眠 → 5. 唤醒后时间补偿

**分数累加器算法**：32768/1000 非整数倍问题 → 累加余数补偿

**LPTIM vs RTC**：
- LPTIM：粒度30μs，分段休眠（16位定时器溢出需处理）
- RTC：粒度1s

**竞态条件防护**：关中断→读就绪表→决定休眠的窗口期必须原子化

### 1.5.1 竞态条件详解（2026-07-31 深挖）

**不关中断的死法**：
```
空闲任务查表 → "没任务，睡 100ms"
  → 正要 WFI 时串口中断来了
  → ISR 唤醒高优通信任务
  → ISR 返回，CPU 带着"睡 100ms"的旧决定进休眠
  → 高优任务被压了 100ms
```

**关中断后**：关中断（BASEPRI）→ 查表（此刻真实状态）→ 执行 WFI（ARM：WFI 自带"同时开中断"）→ 若决策窗口有被堵的中断，WFI 开门的瞬间就被唤醒；无则安全休眠。**本质不是防精度丢失，是防"决策过时"——查表到睡觉之间世界变了但 CPU 不知道。**

### 1.5.2 分数累加器详解

**问题**：LPTIM 32768Hz，每 tick(1ms) 应计 32.768 次，硬件只能计整数。若每 tick 计 32 次，每秒亏 768 次 → 1 分钟后系统时间慢 1.4 秒。

**解法**：累加余数 0.768，当累加值 ≥ 1 时本次计 33 次。单个 tick 不准（32 或 33），长期无累积误差。

```
250ms 示例：余数共欠 250×0.768=192 次
  → 192 tick 用 33 次 + 58 tick 用 32 次 = 8192 次 ✅
```

### 1.5.3 唤醒补偿：累加 vs 重设

**正确做法**：读 LPTIM 实际过的计数值 → 换算 tick 数 → `xTaskIncrementTick()` 批量累加。**不能用直接改写系统时间**——直接改写会让所有延时任务的到期时刻全乱（`vTaskDelay(200)` 被"秒睡"实际一秒没等）。累加做的是"睡觉期间时钟该走多少步，一次性补上"，各任务延时终点不变。

### 1.6 内存管理

**4种 FreeRTOS 内存管理方式**：
- Heap_1：简单分配，不允许释放
- Heap_2：已淘汰
- Heap_3：包装标准 malloc/free（需线程安全）
- Heap_4：默认首选，支持释放合并
- Heap_5：支持不同非连续内存块

**静态 vs 动态**：RTOS 强烈推荐静态内存池 → 分配时间确定、无碎片、适合实时系统

**堆栈分配**：
- 使用 `uxTaskGetStackHighWaterMark()` 检测堆栈使用
- 典型需求：512B~4KB（根据局部变量和函数调用深度调整）

### 1.7 任务间通信

| 机制 | 用途 | 注意 |
|------|------|------|
| 队列 | FIFO数据传递 + 任务同步 | — |
| 信号量 | 资源计数、任务同步 | 二进制信号量有优先级反转风险 |
| 互斥锁 | 互斥访问 | **推荐**，内置优先级继承 |
| 事件组 | 多事件同步 | 任务可等待任意组合 |
| 任务通知 | 轻量级替代信号量 | FreeRTOS中比信号量快45% |

**中断设计原则**：ISR 快进快出，通过任务通知或队列传数据给任务

```c
// FreeRTOS中断发送通知
void IRQ_Handler() {
  BaseType_t xHigherPriorityTaskWoken = pdFALSE;
  vTaskNotifyGiveFromISR(xTaskHandle, &xHigherPriorityTaskWoken);
  portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}
```

## 二、C 语言底层（高频考点）

### 2.1 volatile

**三个使用场景**：
1. 硬件寄存器访问
2. ISR 与主程序共享变量
3. 内存映射 I/O

**三个常见误解**：
- ≠ 原子性
- ≠ 线程安全
- ≠ 内存屏障

### 2.2 const volatile

**使用场景**：只读硬件寄存器（值由硬件改变，软件不能写但每次必须从内存读取）

### 2.3 static 三种语义

1. **函数内**：持久局部变量（生命周期=程序运行期）
2. **文件内**：限制函数/变量作用域为本编译单元
3. **全局**：不可外部链接

### 2.4 函数指针 vs 指针函数

- **函数指针**：`int (*fp)(int, int)` — 指向函数的指针（回调/解耦/多态/状态机）
- **指针函数**：`int* func(int)` — 返回指针的函数

### 2.5 sizeof 陷阱

函数参数中的数组退化为指针 → `sizeof(arr)` 返回指针大小而非数组大小

### 2.6 字节对齐

- `#pragma pack` 改变对齐方式 → 可能导致非对齐访问
- ARM Cortex-M 外设总线：非对齐32-bit访问 → **HardFault**
- 自研RTOS中双核伪共享问题：两个变量同一Cache行 → 性能降40% → 64字节对齐解决

### 2.7 HardFault 排查（裸机四步法）

1. 保存栈帧 → 2. 提取PC（程序计数器）→ 3. CFSR 寄存器诊断（UsageFault/BusFault/MemManage）→ 4. .map 文件反查

### 2.8 GCC 优化等级

| 等级 | 特点 | 自研RTOS实践 |
|------|------|-------------|
| O0 | 无优化，调试用 | — |
| O1 | 基础优化（大小+速度平衡） | — |
| Os | 优化体积 | 内核用 Os，控制在 8KB |
| O2 | 标准优化 | 调度器用 O2 |
| O3 | 激进优化（内联+向量化） | 浮点运算用 O3，曾导致时序问题，用内存屏障解决 |

## 四、中断与实时性

### 4.1 ISR 设计原则

- 快进快出
- 中断中只做必要的事（设标志/发信号量/发任务通知）
- 耗时操作交给任务处理
- 使用 `portYIELD_FROM_ISR()` 在ISR尾部触发任务切换

### 4.2 中断嵌套

- Cortex-M 支持可配置中断优先级
- NVIC 支持抢占（高优先级可打断低优先级ISR）
- 避免过深嵌套 → 增加栈使用和延迟不确定性

### 4.3 DMA vs 中断 vs 轮询

| 方式 | CPU占用 | 延迟 | 适用场景 |
|------|---------|------|---------|
| 轮询 | 高 | 低 | 简单、低频率场景 |
| 中断 | 中 | 低 | 中等数据量 |
| DMA | 低 | 取决于配置 | 大数据量、高吞吐 |

### 8.1 部署全流程

模型训练(Python/TF) → 量化(FP32→INT8) → 格式转换(.h5→.tflite) → TFLM部署 → 推理

### 8.2 关键概念

- **INT8 量化**：将浮点模型转换为8位整数，减小体积、加速推理
- **TFLite Micro**：Google为MCU设计的轻量推理框架
- **算子注册**：TFLM使用算子注册表，可按需编译（减小体积）
- **Arena 内存**：TFLM使用预分配的Arena而非动态分配

### 8.3 端侧AI 定位话术

> "我不是算法科学家，我是算法与硬件之间的桥梁工程师。
> 能做模型部署、能做性能优化、能保证实时性和稳定性。"

### 8.4 模型转换（Keras→TFLite→TFLM）核心概念（2026-07-30 学习）

**训练态 vs 部署态**：
| | 训练时模型 | 部署时模型 |
|:---|:---|:---|
| 前向计算 | ✅ | ✅（唯一需要的） |
| loss / 反向传播 / 优化器 | ✅ | ❌ 全部砍掉 |
| Python 环境 | ✅ | ❌ MCU 跑不了 Python |
| 最终载体 | .h5/.keras（含训练态） | .tflite（纯推理图 FlatBuffer 二进制） |

**xxd / generate_cc_arrays 工作原理**：
- 本质 = 逐字节读取 .tflite → 写成 `0x??,` 格式的 C 数组字面量
- 源码文件 ~38KB（每个字节展成 6 个 ASCII 字符），**编译后 Flash 占用 ≈ 原始 .tflite 大小**（编译器将 `0x??` 还原为单字节，唯一额外开销 = 4 字节长度变量 + 对齐填充）
- 为什么 hex 不用十进制：2 位 hex（`ff`）换 1 字节，与二进制天然 4:1 位映射，是嵌入式通用视觉语言
- 为什么统一 6 字节（`0x00, `）：语法上 0~15 的值只需 4 字节（`0xa,`），但统一置零为 `0x0a,` 保持列对齐——**代码写给人 debug 用的**

**面试话术**（xxd → Flash 全流程）：
> "用 xxd 把 .tflite 逐字节序列化成 C 数组头文件——本质就是把二进制数据写成 `0x??,` 格式的数组字面量，编译后模型待在 Flash 里。TFLM 通过 FlatBuffer 机制直接按偏移访问字段，零拷贝零反序列化。源码看着 38KB 只是文本膨胀，Flash 实际占用 ≈ 原始 .tflite。"

### 8.5 TFLM 算子约束——SELECT_TF_OPS 为什么是陷阱（2026-07-30 学习）

**核心事实**：TFLite（不含 M）和 TFLM 是**两个东西**，算子支持不同。

**SELECT_TF_OPS 的本质**：不是"一组轻量算子"，而是让 TFLite 回头调**完整 TensorFlow 运行时**的粘合层（Flex delegate）。TF 原生算子需要动态内存（malloc）、文件系统（fopen）、Python 运行时、流式 I/O——MCU 全都没有。

**TFLM 的三条底层假设（被 SELECT_TF_OPS 全部打破）**：

| TFLM 假设 | SELECT_TF_OPS 需要的 | 冲突 |
|:----------|:--------------------|:-----|
| 静态内存（tensor_arena 预分配，零 malloc） | 算子内部动态 new/delete | ❌ 崩 |
| 无 OS / 无文件系统 | fopen / 流式 I/O | ❌ 不存在 |
| 极小 Flash 占用（几十~几百 KB） | TF 算子库几百 KB~几 MB | ❌ 放不下 |

**真遇到 TFLM 不支持的算子，解法不是开 Flex**：

| 解法 | 说明 |
|:-----|:-----|
| ① 等价算子替换 | 训练时把 LayerNorm 拆成 Mean→Sub→Mul→Add（TFLM 全支持），重新导出 |
| ② 自定义算子 | 手写 C 实现 + 注册进 OpResolver（⚠️ INT8 场景需保证内核精度） |
| ❌ SELECT_TF_OPS | MCU 上不可能——不是"还没实现"，是实现出来就不是 TFLM 了 |

**面试话术**：
> "SELECT_TF_OPS 不是让 TFLite 支持更多算子，是让 TFLite 借完整 TF 运行时当后盾——这需要动态内存、文件系统和 Python 环境。TFLM 的静态 arena、无 OS、极小 Flash 三条设计前提与它根本不相容。选 TFLM 部署的模型，训练时就要用 TFLM 支持的算子——部署的约束必须前推。"

### 8.6 Netron 验证实操 — 模型B 三层结构实锤（2026-07-30 用 Python TFLite Interpreter 读取验证）

```
模型B (含频域) INT8, 6352 字节

输入: [1, 56]

Dense1 (56→32, ReLU融合):  MatMul[32,56]=1,792 + Bias[32]=32  = 1,824
Dense2 (32→16, ReLU融合):  MatMul[16,32]=  512 + Bias[16]=16  =   528
Dense3 (16→3, Softmax):    MatMul[3,16] =   48 + Bias[3] =3   =    51
                                                          总计 = 2,403 ✅
```

**两个面试加分发现**：
1. **ReLU 在 TFLite 里消失了**：Converter 把 MatMul+BiasAdd+ReLU 算子融合成一个 `FULLY_CONNECTED`——不是 bug，是 TFLite 的图优化（减少内存读写）。所以 TFLM 只需注册 FullyConnected + Softmax 两种算子
2. **权重形状是"反的"**：`[32, 56]` 而非 `[56, 32]`——TFLite 内部做了权重重排，比 Keras 布局快一步 Transpose。面试看到别以为错了

### 8.7 CNN 核心算子与 TFLM 实现（2026-08-04 学习+考核）

**Conv2D 源码核心（6 层 for 循环）**：最内三层（ky/kx/in_c）每次做一次乘加，对 3×3×C_in 个输入通道 × 输出通道——这是乘加次数的爆炸来源。更关键的是**访存模式**：`input[py][px][in_c]` 的 py、px、in_c 都在变→跨行跨通道跳跃→cache miss 频繁（FC 是顺序访问，cache 全命中）。

**MLP vs CNN 乘加次数对比**：

| | MLP（你的模型，2403参数）| 1D CNN（3层Conv+FC）|
|:---|:---|:---|
| 每帧推理乘加次数 | **~4,800 次** | **~50 万次**（百倍）|
| 内存访问 | 顺序读→cache友好 | **滑窗跳跃→cache miss** |

**⚠️ 用户答错记录**：答"MCU 没有加速，CPU 算吃力"——方向对但缺具体数字和访存分析。

**TFLite 两种图优化（面试高频）**：

| 优化 | ReLU 融合 | BatchNorm 折叠 |
|:---|:---------|:--------------|
| **做了什么** | MatMul+BiasAdd+ReLU → 一个 `FULLY_CONNECTED` | **把 BN 的 γ/β/mean/var 四个参数算进 Conv 的权重和偏置里** |
| **原层还在吗** | 标记为内嵌激活函数 | **彻底删除**（Netron 里一线不剩） |
| **公式** | 无变化 | 新W=旧W×γ/√(var+ε)；新B=(旧B-mean)×γ/√(var+ε)+β |
| **原理差异** | 算子合并（不改权重数值） | **常量折叠**（权重数值被改写） |

**⚠️ 用户答错记录**：答"被优化了，具体为什么不知道"→混淆了融合和折叠两个不同的优化机制。

**1D CNN vs MLP 部署负担精确化（串回项目）**：

| 维度 | MLP（现状）| 1D CNN（如改用）| 差异 |
|:-----|:-----------|:---------------|:-----|
| 算子种类 | 2 种 | **4 种**（+Conv2D+MaxPool）|
| 参数量 | 2,403 | **2~5 万** | 10~20× |
| Flash（INT8）| 6,352B | 15~30KB | 2~5× |
| ⚠️ **tensor_arena** | 小（只有向量中间激活）| **大**（每层 Conv 输出整张特征图，如 32×32×32=32,768 个值）| 这里最容易翻车 |
| 推理延迟 | <5ms | 50~200ms | 实时性可能不达标 |

> arena 是隐藏的大头——FC 只有向量，CNN 每层一张特征图，arena 必须容下最大的那张。

### 8.8 Dropout 训练与部署的翻转补偿（2026-08-10 学习+考核）

**核心机制（翻转补偿 Inverted Dropout）**：

| 阶段 | Keras 自动做什么 | 说明 |
|:-----|:-----|:-----|
| `model.fit()` 训练 | 砍掉 p% + 剩余 × 1/(1-p) 放大 | 补偿到训练时做：保持输出总和不变 |
| `model.predict()` 推理 | Dropout 层变透明（pass-through） | 全开，天然就是补偿后的值 |
| `TFLiteConverter` 转换 | **整层删除**（死代码消除） | 推理时永远是 pass-through → 安全删除 |

**为什么推理时不需要补偿**：不是"跳过补偿"——是**补偿在训练时已经做完了**。剩余的神经元被放大了 1/(1-p) 倍，推理时全部神经元本来就是完整值，不需要乘任何东西。翻转方案让"训练"和"部署"完全解耦——TFLM 根本不需要知道训练时用了多少 Dropout。

**⚠️ 用户答错记录**：答"推理时没有 Dropout 了"——结论对但误以为"不需要补偿"是凭空跳过的，实际是训练时已翻转补偿。

**面试话术**：
> "Dropout 用翻转补偿——训练时幸存神经元乘 1/(1-p) 保持输出总和不变，推理时全部神经元都开，天然就是补偿后的值。所以 TFLite Converter 能直接把 Dropout 层当成死代码删除——和 BatchNorm 折叠一样，都让部署模型和训练模型解耦。"

### 8.9 优化器选型：SGD vs Adam（2026-08-10 学习）

| 维度 | SGD | Adam |
|:-----|:-----|:-----|
| 原理 | W = W - lr × gradient（固定步幅） | 自适应步幅（存动量 m + 方差 v，每个参数独立调整） |
| 收敛速度 | 慢 | 快 |
| 泛化能力 | **通常更好**（简单模型不过拟合） | 可能差（参数太灵活，死记噪声） |
| 内存 | 低 | 3 倍（存 W + m + v） |
| 调参 | 需手动调 lr | 默认参数通常够 |
| 嵌入式场景 | ✅ 追求最终精度 | ⚠️ 小数据易过拟合 |

**部署精度 ≠ 训练精度**：Adam 可能训练集 95%→部署 88%（记了噪声），SGD 训练 93%→部署 92%（学了真模式）。2% 差异在论文是数字，在产品是用户每分钟多 3 次误判。

**面试话术**：
> "优化器选型不是理论的，是部署精度的。Adam 训练快但容易记住训练数据的噪声，部署到新数据上掉点严重；SGD 收敛慢但泛化好。嵌入式场景数据少、部署环境多变，SGD 的稳健性比 Adam 的快收敛更重要。这和嵌入式代码一个道理——仿真器跑通不等于上板不挂。"

## 九、Cortex-M 启动流程与 Boot/App 跳转（2026-07-29 学习+考核）

> 已有基础：《嵌入式基础.docx》（向量表/四步曲已覆盖），本笔记为面试深度补充 + 实战易错点。⚠️ = 用户实际答错过的内容，面试高危。

### 9.1 上电启动硬件序列（面试必问）

| 步骤 | CPU 动作 | 来源 | 常见误区 |
|:-----|:---------|:-----|:---------|
| 1 | 从 `0x00000000` 读取 **MSP 初值**（栈顶） | 向量表第 0 项 | ⚠️ 误记为"复位向量"——第 0 项是栈顶，第 1 项才是复位向量 |
| 2 | 从 `0x00000004` 读取 **PC = Reset_Handler** | 向量表第 1 项 | ⚠️ 地址值是**奇数**（bit0=1 = Thumb 状态位，实际地址 = 值 & 0xFFFFFFFE） |
| 3 | 跳到 Reset_Handler | — | 第一条 C 指令就要压栈 → 必须先有栈（MSP） |

**为什么先 MSP 再 PC**：任何 C 代码立即用栈（局部变量/函数调用），中断随时可能发生——硬件必须在执行代码前把栈备好。

### 9.2 Reset_Handler 四步曲（startup.s）

```
① 拷贝 .data 段：Flash(LMA) → RAM(VMA)，用链接器符号 _sidata/_sdata/_edata
② 清零 .bss 段：_sbss ~ _ebss 填 0
③ 调用 SystemInit()：配置时钟树（HSE→PLL→SYSCLK）
④ 调用 __main → 最终进入 main()
```

⚠️ **Keil 的坑**：ARMCC 库把 ① ② 封装在 `__main → __scatterload` 里，.sct 文件声明段属性，库自动做拷贝——所以 Keil 用户看不到显式循环，容易以为"启动代码没做拷贝"。

### 9.3 段与变量存储模型

| 段 | 内容 | 存在哪 | 启动处理 | 未初始化时的值 |
|:---|:-----|:-------|:---------|:---------------|
| `.data` | `int x=5;`（有初值全局/静态） | 运行时 RAM，初值 Flash | Flash→RAM 拷贝 | 就是初值 5 |
| `.bss` | `int y;`（无初值全局/静态） | RAM | **清零** | 始终 0 |
| `栈` | 函数内 `int z;`（局部变量） | RAM（SP 指向） | **不管** | ⚠️ **随机垃圾** |

⚠️ **用户连续答错记录**：① "局部变量启动时清零"→ 错误，局部变量在栈上，不归启动代码管，未初始化 = 随机值；② "MSP 非系统用、PSP 系统用"→ 完全说反，MSP = 异常/中断用（主栈），PSP = 任务线程用（进程栈）。

### 9.4 Boot + App 双区架构

**经典布局**：
```
0x08000000  ┌──────────┐
            │  Boot    │  永不自擦，升级守护
0x08004000  ├──────────┤
            │  App     │  向量表+代码+数据
0x08020000  ├──────────┤
            │  参数区   │  升级标志/版本号（独立扇区）
            └──────────┘
```

**Boot 跳 App 五步曲 + 每步的"为什么"**：

| 步 | 操作 | 不做的后果 |
|:---|:-----|:-----------|
| ① 关中断 | `__disable_irq()` | ⚠️ 跳转瞬间来中断→CPU 按旧向量表找 ISR→已 deinit 的逻辑/被覆盖的数据→死机 |
| ② deinit | 关 SysTick/外设时钟 | App 初始化时面对"脏现场"（SysTick 已在跑 → HAL_GetTick 错乱） |
| ③ `__set_MSP(app_msp)` | 设 MSP = App 向量表第 0 项 | ⚠️ App 第一条 C 指令 PUSH 就压栈→MSP 还是 Boot 的→压到 Boot 栈区→数据污染/HardFault |
| ④ `SCB->VTOR = APP_ADDR` | 重定向中断向量表 | ⚠️ App 运行后中断来了→CPU 还查 Boot 向量表→ISR 地址是空/过期逻辑→中断全废 |
| ⑤ 函数指针跳转 | `((void(*)(void))app_reset)()` | bit0=1 已由链接器保证 |

**本质洞察**：Boot 跳 App = 软件重演硬件启动（读 MSP→读 PC→执行），唯一多一步 **VTOR**（硬件默认 VTOR=0，软件换家必须改门牌号）。

### 9.5 常见事故场景（面试举例题源）

| 事故 | 根因 | 死法 |
|:-----|:-----|:-----|
| 跳转后中断全废 | 忘设 VTOR（题 2） | App 逻辑正常但任何中断都不进/跳错函数 |
| 一跳就 HardFault | MSP 没设或设错 | 第一条 PUSH 就访问非法地址→Fault 嵌套→Lockup |
| HAL 时基卡死 | Boot 的 SysTick 没关 | 两个 SysTick 抢拍，HAL_GetTick 值不可预期 |
| MSP=非法地址 | 向量表第 0 项写错 | 压栈→BusFault→Fault 入场再压栈（还是非法 MSP）→Lockup（复位-死机循环） |

### 9.6 升级标志存放策略（2026-07-29 讨论深挖）

⚠️ **核心禁地**：不能放普通 `.bss` 全局变量——软复位后启动代码清零 `.bss`，标志丢失。

**两种架构方案**：

| | 方案 1：固件预存 Flash | 方案 2：Boot 在线接收 |
|:---|:---|:---|
| 流程 | App 收完固件→存备份区→写标志到 Flash→重启→Boot 搬 | App 写标志→软复位→Boot 与上位机握手→边收边写 |
| 标志位置 | Flash 标志页 | no-init RAM / 备份寄存器 / 备份 SRAM（省擦写），也可放 Flash |
| 断电安全 | ✅ 固件已在 Flash | ❌ 擦写中断电=变砖（除非 A/B 双区） |
| 缺点 | 需备份区≈App大小 + 多一次搬运 | 上位机必须等握手 |

**STM32F4 三个物理位置**：

| 方案 | 地址 | 写操作关键 | 适合 |
|:-----|:-----|:-----------|:-----|
| RTC 备份寄存器 | `0x40002850` | 开 PWR 时钟 + `PWR_CR_DBP` 解锁 | 少量标志 + 有电池 |
| 备份 SRAM | `0x40024000` (4KB) | 使能 BKPSRAM 时钟 + DBP | 断点续传进度 + 有电池 |
| **no-init RAM** | 链接脚本 `UNINIT` / `(NOLOAD)` | ⚠️ **双端工程都要配**（只配一端，另一端启动照样清零）| 纯抗软复位 + 零硬件成本 + **必须用魔数防上电随机值** |

### 9.7 链接脚本核心概念

| 概念 | 含义 | 关键 | 
|:-----|:-----|:-----|
| **LMA**（加载地址） | 段在 Flash 中的存储位置 | `.data` 的 LMA=Flash（存初值），VMA=RAM（运行时读写） |
| **VMA**（运行地址） | 段运行时的地址 | `.bss` 只有 VMA，无 LMA（不占 Flash） |
| **链接器符号** | `_sdata / _edata / _sidata / _sbss / _ebss` | ⚠️ 不是 C 变量！是链接器算出的地址常量，启动代码用 `&_sdata` 取地址 |
| `NOLOAD` / `UNINIT` | 无加载/不清零段 | no-init 区由此实现——跳过 Flash 分配 + 启动不清零 |
| `KEEP()` | 强制保留段 | `.isr_vector` 必用 `KEEP`，否则 `--gc-sections` 会回收 |

**工具链对照**：

| | GCC | Keil(ARMCC) | IAR |
|:--|:----|:------------|:----|
| 文件 | .ld | .sct | .icf |
| .data 装载 | `> RAM AT> FLASH` | 分散加载自动 | `initialize by copy` |
| no-init | `(NOLOAD)` 段 | `UNINIT` 执行区 | `do not initialize` |
| .data 拷贝 | 用户启动代码显式拷贝 | 库 `__scatterload` 自动 | 库自动 |

### 9.8 今日考核易错汇总（⚠️ = 用户实际答错）

| 知识点 | 错误表述 | 正确表述 | 错误次数 |
|:-------|:---------|:---------|:---------|
| MSP/PSP 归属 | "MSP 非系统用，PSP 系统用" | **MSP = 异常/中断用（主栈），PSP = 任务线程用（进程栈）** | 2 次 |
| 局部变量初始化 | "局部变量启动时清零" | 局部变量在栈上，启动流程不管它，未初始化 = **随机值** | 1 次 |
| 全局未初始化变量 | 和局部变量混淆 | 全局未初始化 → `.bss` → 启动**清零** = 始终 0 | 1 次 |
| 升级标志丢失原因 | "掉电丢失，放 Flash" | 软复位不断电，RAM 不清零——真正原因：**启动代码 .bss 清零抹掉了标志** | 1 次 |
| 跳转前关中断原因 | "中断找不到 ISR" | 更精确：跳转瞬间中断来→CPU 按旧向量表找**旧 ISR**→ISR 已 deinit 释放资源→执行过期逻辑→死机 | 1 次 |
| 复位向量位置 | "向量表第一项" | 第 0 项是 MSP 初值，**第 1 项（偏移 0x04）才是复位向量** | — |
| Reset_Handler 地址 | 没注意到是奇数 | bit0=1 = Thumb 状态位，实际地址 = 值 & 0xFFFFFFFE | — |

### 9.9 面试速查（高频问 → 答法要点）

| 面试题 | 答法骨架 |
|:-------|:---------|
| 上电后 CPU 做的第一件事？ | 读 MSP（栈顶）→ 读 PC（Reset_Handler）→ 跳到 startup.s。先设栈是因为 C 代码和中断立刻要用栈 |
| Reset_Handler 做了什么？ | 四步：.data 拷贝（Flash→RAM）、.bss 清零、SystemInit（时钟）、进 main |
| `int x=5` vs `int y` vs 局部变量？ | .data 拷贝 / .bss 清零 / 栈上随机值 |
| Boot 跳 App 的步骤？ | 五步：关中断→deinit→设 MSP→设 VTOR→跳转。本质 = 软件重演硬件启动 |

| 链接器符号怎么用？ | 不是变量，是链接器算的地址常量。启动代码 `&_sdata` 取地址做拷贝；改链接脚本，符号自动跟着变
| `.data` 写在 `> FLASH`（没 `AT>`）会怎样？ | LMA = VMA = Flash → 运行时无法写，全局变量全部只读，程序行为完全不可预期 |

## 二、核心经验（按优先级排列）

### 🥇 经验1：回答必须展现"工程师思维"，而非"知识复述"

**描述**：MS官对不同年限的工程师有不同预期。3年能答出"是什么"就可以，但8年以上必须答出"为什么这么做 + 踩过什么坑 + 还有更好的方法"。回答停留在教科书式知识复述，在资深岗MS中等于不及格。

**教训**：
- 我的一面回答"每道题都知道，但没达到MS官预期"
- MS官心里在对照JD逐条打勾，你要帮他找到你的"深度标签"

**改进方法** — 四步回答法：
```
问题本质（一句话点透）→ 我的实践（真实项目+数据）→ 踩过的坑（这才是区分点）→ 我的思考（升华）
```

| 问题示例 | ❌ 普通回答 | ✅ 高分回答 |
|:---------|:----------|:----------|
| GCC优化等级 | 讲O0/O1/O2/Os/O3各自做了什么 | "本质是速度/大小/调试的权衡。自研RTOS时内核用Os控制8KB内，调度器用O2，浮点运算用O3开向量化。但-O3出过问题——延时循环被优化掉了导致外部芯片时序不满足，最后用__asm__ volatile内存屏障解决" |
| 优先级反转 | 讲继承和天花板两种方法 | "先讲火星探路者案例。自研RTOS实现了优先级继承，但发现链式反转问题——多模块嵌套锁导致继承链断裂，偶发死锁。后来在编码规范里要求优先用消息队列代替共享内存，从架构层面规避" |
| Cache问题 | 讲数据一致性/伪共享 | "双核项目遇到伪共享——两个变量同一Cache行导致性能降40%，用64字节对齐解决" |

**出处**: [[ninebot-deep-review]] 第一、二、三节

### 🥈 经验2：项目介绍 — 第一句话就给技术标签

**描述**：MS官不会给你3分钟从头到尾讲项目。前15秒如果没让他听到"硬核技术点"，他会走神或直接打断。第一句话必须是**一个技术标签式结论**。

**教训**：
- 青鸟初面：介绍项目"整体框架→被说没看到细节→开始补充→还没讲完被挂断"
- MS官要的是"你解决过什么难的问题"，不是"你做了多少事情"

**改进方法** — 每个项目准备"一句话技术标签"：

| 项目 | 一句话技术标签 |
|:-----|:-----|
| 自研RTOS | "从零到一自研轻量级RTOS，跨ARM M4和DSP双平台，内核ROM 5KB/10KB，支持Tickless低功耗" |
| 爱博精电电力仪表 | "基于Cortex-M4的多通道ADC采样+实时数字滤波+MODBUS协议栈，误差精度达X级" |
| H3C交换机产品 | "负责XG交换芯片驱动适配、数据面转发Pipeline调优、产测工装全自动化开发" |

**我最有代表性的项目**，是从零到一自研的轻量级实时操作系统，目前已经落地在工业控制产品上。
整个项目我是核心负责人，从内核架构到驱动体系全程主导：内核层面实现了抢占式调度器、信号量、消息队列、内存管理，针对低功耗场景做了 Tickless idle 机制，用分数累加器算法解决了低功耗定时器的时间漂移问题，最终内核 ROM 仅 5KB(ARM M4)/10KB(DSP)，待机功耗做到了个位数微安。
驱动层面我搭建了统一的驱动抽象层，像 CAN/CAN FD、DMA、定时器、ADC 这些常用外设都做了标准化适配，还针对 CAN FD 的双波特率做了精细化的位时序校准，把总线负载从 70% 降到了 20% 多，大幅提升了多节点通信的稳定性。
另外从产测工装到现场问题排查，全流程我都跟过，很清楚量产产品和 demo 的区别，对可靠性、可维护性这块考虑得比较多。
您想重点了解内核、驱动还是低功耗哪一块的细节，我可以展开讲。

### 经验3：把"自研RTOS"打造成你的最强武器

**描述**：自研RTOS是你区别于"会用RTOS的普通嵌入式工程师"的最强标签。MS中遇到的几乎所有技术问题，都应该往这上面引。

**改进方法**：
- 问编译优化 → "自研RTOS时内核Os编译，调度器O2，体积控制8KB以内"
- 问优先级反转 → "自研RTOS实现了优先级继承，编码规范要求避免锁使用"
- 问Cache问题 → "自研RTOS做了DMA前后的Cache一致性优化"
- 问低功耗 → "自研RTOS原生支持Tickless，基于LPTIM，待机功耗不到10uA"

**定位转变**：从"懂很多技术的工程师"变成"从零到一做过底层平台的资深专家"。

### 经验4：用STAR-R法则重构每个项目回答

**描述**：Situation → Task → Action → Result → Reflection，比STAR多一个Reflection（反思），展现你的持续学习能力。

```
S — 背景：电力仪表需要25Hz采样率，CPU还要处理通信和显示
T — 任务：在保证采样实时性的同时让其他任务正常执行
A — 行动：设计三级优先级（采样5>通信3>显示1），DMA+双缓冲，环形缓冲通信
R — 结果：采样抖动从±15us降到±2us，通信不丢帧
R — 反思：如果重做，用DMA半满中断进一步减小延迟
```

**出处**: [[ninebot-review]] 2.1节"工程化深度不够"

### 经验5：C语言底层理解必须补到"能讲清楚边界场景"

**描述**：8年经验不该停留在"能说出是什么"，而要能讲清边界场景和常见误解。

| 知识点 | 必须能说清 |
|:-------|:----------|
| volatile | 三个使用场景 + 三个常见误解（不等于原子性、不等于线程安全、不等于内存屏障） |
| const volatile | 同时使用的场景：只读硬件状态寄存器 |
| static | 函数内/文件内/全局三种语义 |
| 字节对齐 | 原理 + #pragma pack副作用 + 非对齐访问→HardFault |
| 指针函数 vs 函数指针 | 区别要能脱口而出 |
| sizeof陷阱 | 数组做函数参数时退化为指针 |

**出处**: [[ninebot-review]] 2.2节；[[ninebot-questions]]

### 经验6：识别"套经验"面试——JD 与面试内容不符就是反向筛选信号

**描述**：HR 说招 MCU RTOS 人才，面试官却全程不问 MCU/RTOS，一直追问 TSN 交换机、时间同步；问到 SyncE 频率传递这种底层机制时，对方"牛头不对马嘴"，听不懂你的解释还质疑你（实际上你说的是对的——SyncE 频率就是通过物理链路 CDR 逐跳传递的）。

**教训** — 两个信号识别套经验面试：
- 信号1：**JD 与面试内容严重不符**（说招 MCU RTOS，却全问 TSN）
- 信号2：**面试官无法对等地往下追问**（你说 Qbv 门控列表，对方零回应；说 SyncE 频率传递，对方听不懂还质疑）

**改进方法** — 反向筛选三问（面试前/中快速判断值不值得认真准备）：
1. 面试官问的是不是「我简历上的主项」？（偏离主项 = 临时起意套经验）
2. 面试官能不能「对等地往下追问」？（能追问 = 真懂；听不懂还质疑 = 套经验）
3. 对方是真招人还是"技术咨询会"？（一直问实现原理却无回应 = 白嫖方案）

**收获**：这类面试的价值是反向确认了稀缺标签（TSN）连来套经验的人都挖不动。不必为它投入大量准备时间——真正值得去的地方，是能和你对等深挖主项的公司。

**⚠️ 复盘补充（也有我的沟通责任）**：对方听不懂，也有我的责任——我直接说"频率通过链路传递"，但"链路"这个词在 OSI 不同层有歧义：我说的是**物理层 L1 的串行码流**，对方脑子里是**数据链路层 L2 的数据包**。没先锚定层级就下结论，导致错位。

**沟通技巧（所有底层技术题通用）**：讲底层技术**先锚定层级，再讲机制**——先甩一句"我说的是物理层 L1 的码流，不是 L2 的数据包"，把概念对齐，再讲频率在码流跳变边沿里、CDR 恢复、跟数据包无关。跳过"对齐"直接讲结论，对方就可能在另一层理解你。

**出处**: 千寻智能一轮技术面（2026-09-02）

### 经验7：端侧AI必须动手实践，不能只看课程

**描述**：千寻面试被问「数据如何标注的」，回答"用训练数据、自定义 1 2 3 分类"——模糊，暴露了"没真做过"。

**教训**：
- 端侧 AI 这类"有产出物"的方向，看课程/看文档 ≠ 会做。面试官一问实操细节（数据标注、量化、部署），没真做过的人立刻穿帮。
- "用训练数据"是空话（标注本来就是处理训练数据的过程）；"自定义 1 2 3 分类"说不清标注方法/工具/质量，等于没答。

**改进方法**：
- 端侧 AI 必须跑通一个完整实战（采集→标注→训练/量化→部署→推理），每个环节的实操细节都能讲出来。
- 数据标注正确概念（补认知）：给原始数据打标签供监督学习。方式=人工/半自动/规则自动；工具=LabelImg/CVAT/doccano；质量=交叉标注+一致性检查（garbage in garbage out）。端侧异常检测常用"只有正常数据"的无监督（one-class/重建误差），无需大量标注——这是能体现深度的点。

**出处**: 千寻智能一轮技术面（2026-09-02）

#### TSN 稀缺能力战略（2026-09-02 千寻面试后反思）

**判断**：TSN 协议原理（Qbv/Qci/Qbu/CB/gPTP）+ SyncE + PTP 是**极度稀缺的能力**——国内真正系统做过 TSN 完整协议栈的工程师极少。这次千寻面试反向印证：连临时来套经验的公司都挖不动你的 TSN 储备（说 Qbv 对方零回应、说 SyncE 频率传递对方听不懂还质疑）。

**后续需要实践深化**（把"技术储备"变成"能对等深挖的深度"）：
1. SyncE：补上「码流(L1) vs 业务帧(L2) + CDR + IDLE 空闲码」底层机制（已归档 TSN 文档）
2. PTP/gPTP：补上「PHY/MAC 硬件时间戳 + BMCA 选主算法」底层实现（已归档 TSN 文档）
3. Qbv/Qci/Qbu/CB：补上令牌桶、门控列表、帧抢占、冗余的底层原理
4. 实践方向：把 TSN 协议栈在真实硬件（交换机/网卡）上跑起来，或做技术沉淀，把"做过"变成"有产出物证明"

**这是未来的值钱地方**：汽车（车载以太网 TSN）、工业（确定性网络）、机器人（多关节实时通信）都在往 TSN 走，而国内能做的人极少。**TSN + 自研 RTOS 两个稀缺标签叠加**，是你区别于"普通嵌入式工程师"的核心壁垒。

---

> **一句话总结**：你不是找不到工作，是之前投的岗位恰好是既卷、薪资低、又不匹配你核心优势的赛道。换个靶心、做一个端侧AI实战项目、MS时把"自研RTOS+端侧AI"两个标签同时打出来——体感会完全不一样。

# CAN 应用层协议设计总结（2021 爱博精电 IO 模块）

> 来源：`CAN应用层协议说明文档_20211201.docx` + `IO模块CAN通信BOOT报文_20211202.xlsx`
> 一句话定位：**29-bit 扩展帧 ID 做语义化路由 + 8 字节数据负载**，主从问答式工业 CAN 应用层协议。

## 一、协议总览

| 维度 | 内容 |
|------|------|
| 帧格式 | **经典 CAN 2.0B（29-bit 扩展帧）**，非 CAN FD |
| 单帧负载 | **最多 8 字节**（数据1~数据8） |
| 交互模式 | 主从问答（主机命令 + 从机应答/无应答） |
| 数据字节序 | 多字节数据**小端传输** |

## 二、CAN 协议字段 ↔ 项目 bit 位映射（核心）

CAN 2.0B 扩展帧的**仲裁场（Arbitration Field）**结构：

```
SOF | Base ID[10:0] | SRR | IDE | Ext ID[17:0] | RTR | r1 | r0 | DLC[3:0] | 数据场(0~8B) | CRC | ACK | EOF
     └────── 11 bit ──────┘            └── 18 bit ──┘
     └──────────────────── 29-bit 标识符（ID）────────────────────┘
```

**项目的 29-bit ID 全部位于 CAN 的"仲裁场·标识符"字段**，内部再拆成 8 个位域：

| 项目位域 | 位宽 | ID 位序号 | 对应 CAN 协议字段 |
|:---------|:-----|:----------|:------------------|
| 优先级 | 5 Bit | Bit28~24 | Base ID[10:6] |
| 预留 | 4 Bit | Bit23~20 | Base ID[5:2] |
| 广播位 | 2 Bit | Bit19~18 | Base ID[1:0] |
| 报文类型 | 1 Bit | Bit17 | Ext ID[17] |
| 主/从 | 1 Bit | Bit16 | Ext ID[16] |
| 模块类型 | 4 Bit | Bit15~12 | Ext ID[15:12] |
| 模块地址 | 4 Bit | Bit11~8 | Ext ID[11:8] |
| 报文编号 | 8 Bit | Bit7~0 | Ext ID[7:0] |

> 关键记忆：**前 11 bit（优先级+预留+广播）= Base ID；后 18 bit（报文类型+主从+模块类型+地址+编号）= Ext ID**，正好 11+18=29。

各字段含义：

| 字段 | 取值 | 含义 |
|------|------|------|
| 优先级 | 0~31 | 0=最高（主机控制命令），31=最低（从机应答） |
| 预留 | — | 统一填 1（便于数据管理） |
| 广播位 | 00 / 11 | 00 普通帧 / 11 广播帧 |
| 报文类型 | 0 / 1 | 0 通用帧 / 1 管理帧(BOOT) |
| 主/从 | 0 / 1 | 0 从机数据 / 1 主机数据 |
| 模块类型 | 0~0xF | 模块类型 |
| 模块地址 | 0~0xF | 模块逻辑地址 |
| 报文编号 | 0~0xFF | 组合报文编号 |

## 三、为什么这样设计（面试亮点）

1. **优先级放 ID 最高位，白嫖 CAN 硬件仲裁**
   CAN 仲裁规则是"ID 越小优先级越高"。把优先级字段放在 Bit28~24（ID 最高位），优先级值越小 → 整个 ID 越小 → 总线仲裁自动先发。**零软件开销实现应用层优先级调度**。

2. **ID 语义化路由，不占数据带宽**
   用 ID 承载"谁发给谁 / 什么类型 / 什么报文"，8 字节数据区全留给负载。比"把状态编进 ID"更高效——ID 本就随帧免费传输，用它做寻址不挤占数据区。

3. **管理帧(BOOT)独立通道**
   报文类型位区分通用帧 / 管理帧，BOOT 升级走独立 ID 空间，与业务数据隔离，互不干扰。

4. **主从问答 + 广播/点对点复用**
   广播位支持一对多下发；模块类型 + 模块地址支持点对点寻址。

## 四、应用场景与通讯流程

**4 类应用场景**：① IO 信息（DI 上传 / DO·RO 下置）② SOE 记录 ③ 模块 BOOT 升级 ④ 打印机等长帧通信。

**3 类通讯流程**：

| 阶段 | 内容 | 应答 |
|------|------|------|
| 上电 | 序列号 → 版本信息 → 配置信息 | 均带应答 |
| 实时交互 | 心跳、DI/SOE 上传、DO/RO 下置 | 无应答 |
| 非实时 | 读版本号 / 序列号等出厂信息 | 带应答 |

## 五、BOOT 报文速览

| 方向 | 优先级 | 报文编号 | 功能 |
|------|--------|---------|------|
| 主机→从机 | 0 | 1 | 重启（0xF2） |
| 主机→从机 | 0 | 2 | 请求编程（0x72 0xA5） |
| 主机→从机 | 0 | 3 | 建立连接（0xAA 0xAA + 超密） |
| 主机→从机 | 0 | 5 | 擦除 ROM |
| 主机→从机 | 0 | 6~8 | 编程数据指令 / 编程数据 / 编程结束 |
| 主机→从机 | 0 | 9 | 更新系统（0xF3） |
| 从机→主机 | 31 | 1~11 | 各命令对应应答 |

## 六、⚠️ 面试口径区分

- 本协议 = **经典 CAN 2.0B**（8 字节负载，29-bit 扩展帧）
- 简历里的 "CAN FD 双波特率、负载 72%→21%" = **另一个项目**，面试别混成一个项目讲。

## 七、优先级：两层机制 + 诚实面试说法

本项目只做了**一层**（ID 仲裁层），别和软件队列层混为一谈：

| 层面 | 机制 | 本项目是否实现 |
|------|------|---------------|
| **ID 仲裁层**（跨节点） | 优先级字段放 ID 最高位，靠 CAN 硬件仲裁，ID 小者先发 | ✅ 已实现 |
| **软件发送队列层**（节点内） | 多级 FIFO + 高优先级插队 + 配合发送邮箱 | ❌ 未实现（节点少、帧量小，ID 仲裁已够） |

**诚实面试说法（既诚实又完整）**：

> "我的项目做了 ID 层的优先级设计——把优先级字段放在 29-bit ID 最高位，靠 CAN 硬件仲裁实现跨节点的优先级调度。软件层的多优先级发送队列是标准的工程化做法（多级 FIFO + 高优先级插队 + 配合发送邮箱），这是我对完整方案的认知，但当年那个项目因为节点少、帧量不大，主要靠 ID 仲裁就够了，没上多级软件队列。"

## 八、接收路径优化：ID 语义化让硬件过滤高效

CAN 接收性能优化三层：**少进中断（硬件过滤）→ 进了不丢（双 FIFO）→ 进完快出（中断底半部）**。其中**硬件过滤和你项目的 ID 语义化设计是天然联动**，是最能讲的亮点。

### 8.1 硬件过滤原理

CAN 是广播总线，不过滤则总线上每帧都触发 CPU 中断，节点越多 CPU 被无效中断淹没。CAN 外设内置**硬件过滤器**，在硬件层按 ID 判断"是不是我要的帧"，不要的直接丢弃，**不给 CPU 发中断**。

| 过滤器模式 | 规则 | 适合场景 |
|-----------|------|---------|
| **ID 列表模式** | 指定 N 个具体 ID，只收这几个 | 只关心零星几个报文 |
| **掩码模式** | ID + 掩码，掩码=1 的位必须匹配，=0 忽略 | 收"一段 ID 范围" |

### 8.2 联动亮点：ID 语义化 → 掩码过滤天然高效

你的 29-bit ID 是「模块类型(4bit) + 模块地址(4bit) + 报文编号…」语义化拆分，这天然适合**掩码过滤器**：

- 本模块是「模块类型=3、地址=5」，就把掩码设在「模块类型 + 模块地址」这 8 位上
- 硬件自动只放行「发给类型 3 地址 5 的帧 + 广播帧」，其余全在硬件层扔掉，不产生中断
- **一个掩码过滤器覆盖"所有发给本模块的帧"**，不用为每个报文编号单独配过滤器

**面试话术（背）**：

> "我的 29-bit ID 把模块类型、模块地址放在固定位域，这正好和硬件掩码过滤器配合——掩码设在类型+地址这 8 位上，硬件自动只放行发给本模块的帧和广播帧，其余不产生中断。等于用 ID 的语义化设计，白嫖了 CAN 硬件的接收过滤能力，CPU 只处理真正发给自己的帧。"

> ⚠️ 诚实边界：这是**设计层面的联动**（ID 语义化天然支持硬件掩码过滤）。实际项目是否显式配置了掩码过滤器，视当年代码而定；若被追问，如实答"设计上支持，实际节点少时靠默认接收 + 软件判断 ID 也够，掩码过滤是标准优化手段"。

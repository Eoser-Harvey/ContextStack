# 交换机 ping 丢包排查方法论（附 IE4120U 实战案例）

> 一句话定位：**ping 丢包 = 路径上某处 request 或 reply 被丢弃/延迟**。排查本质是「分层定位 × 逐跳隔离 × 双向验证」，锁定"哪一跳、哪个方向、哪个原因"。
> 本文前半讲通用方法论，后半用 **IE4120U 弱管交换机**客户案例演示完整落地。

## 一、总纲

三条铁律：

1. **先定形态，再动手**——搞清楚"谁 ping 谁、同段还是跨段、几跳"，方向错了全盘皆输。
2. **单点抓包必误判**——必须多点同时抓 + 分方向核对。
3. **现象 ≠ 根因**——"PC 没回 reply"是现象，不是结论；要追问"为什么没回"。

## 二、六步排查框架

### 第 1 步：先定「形态」

| 维度 | 分类 | 决定什么 |
|:-----|:-----|:---------|
| 谁 ping 谁 | 交换机→终端 / 终端→交换机 / 终端→终端 | 是否涉及 CPU |
| 路径 | 直连 / 单跳 / 多跳 / 跨 VLAN | 逐跳隔离的范围 |
| 丢的方向 | 只丢 request / 只丢 reply / 双向都丢 | 归属哪台设备 |

### 第 2 步：区分「转发面」还是「控制面」（交换机特有，最关键）

这是交换机分析区别于普通主机的**核心分叉**，搞错方向全盘皆输：

| 场景 | 报文怎么走 | 丢包优先怀疑 |
|:-----|:-----------|:-------------|
| PC ping PC（同网段） | 纯硬件转发，**不过 CPU** | 端口错包 / MAC 表 / 拥塞 |
| **交换机 ping 终端** | CPU 发 request → 转发面出去；reply → 转发面进来 → **上送 CPU** | CPU 忙、上送限速 |
| ping 交换机自身管理 IP | 全程上送 CPU | CPCAR 限速、CPU 打满 |

**判断口诀**：交换机自己发起的 ping 丢包 → 先查 `display cpu-usage`；PC 之间丢包 → 先查端口统计和表项。

> 实战价值：交换机发起 ping 要**两次穿越 CPU**，所以"交换机 ping 丢、PC ping 不丢"直接指向控制面问题，与终端无关。

### 第 3 步：自底向上逐层排查

| 层 | 检查点 | H3C 关键命令 | 典型症状 |
|:---|:-------|:-------------|:---------|
| 物理层 | 端口 up/down 抖动、CRC、双工 | `display interface` | 错包增长、半双工 |
| 物理层 | 光模块光衰/温度 | `display transceiver diagnosis` | 光衰临界间歇中断 |
| 链路层 | MAC 表项、ARP | `display mac-address` / `display arp` | 表项缺失、频繁泛洪 |
| 链路层 | 环路/拓扑 | `display stp brief` / `display stp abnormal-port` | STP 未开或反复收敛 |
| 链路层 | 广播/组播风暴 | `display storm-constrain` / 抓包看 ARP 速率 | CPU 被广播打满 |
| 网络层 | 路由、VLAN 透传 | `display ip routing-table` / `display vlan` | 路由黑洞、VLAN 不通 |
| 网络层 | ACL/策略/隔离 | 查下联口配置 | 误拦 ICMP |
| 控制面 | CPU/内存 | `display cpu-usage` / `display memory` | CPU 持续高位 |
| 控制面 | 上送限速 | CPCAR / 上送策略 | ping 交换机自身丢包 |
| 拥塞 | 队列丢包、缓存 | `display counters` / `display qos queue-statistics` | 突发流量丢包 |

### 第 4 步：双向抓包锁定方向

单点抓包会误判，正确做法是**同一时刻多点抓 + 分方向核对**：

```
抓包点：源侧出口 | 中间节点上联口 | 中间节点下联口 | 目的侧
核对：  request  ↓       ↓              ↓            ↓（到了没）
        reply    ↑       ↑              ↑            ↑（回了没）
```

| 抓包现象 | 结论 |
|:---------|:-----|
| request 到目的、reply 没回来 | 目的侧没回（但还要追"为什么没回"） |
| request 都没到目的 | 中间丢，逐跳往前缩 |
| request 在源侧就没了 | 源侧路由/ARP/上送问题 |

> 关键认知：**在目的侧（如 PC 本机）抓包**，只能证明"PC 收到 request 但没回 reply"，**无法区分**是"PC 不想回"还是"PC 回不了"（如 ARP 解析失败）。要追到"为什么没回"。

### 第 5 步：常见根因速查

| 根因 | 特征指纹 | 验证手段 |
|:-----|:---------|:---------|
| ARP 风暴/扫描 | 抓包 ARP 速率异常高、源 OUI 集中 | 抓包统计源 MAC/IP 排行 |
| 环路 | STP 反复收敛、MAC 表震荡 | `display stp abnormal-port` |
| CPU 打满 | 只有交换机 ping 丢，PC-PC 不丢 | `display cpu-usage` |
| 端口错包/半双工 | input/output errors 增长 | `display interface` |
| MAC 表溢出 | 下挂大量终端、未知单播泛洪 | `display mac-address count` |
| 上送/ICMP 限速 | ping 交换机自身丢、ping 终端不丢 | 查 CPCAR 配置 |
| 终端侧 | 网卡 EEE 节能、防火墙、EDR | PC-PC 对比、换终端 |

### 第 6 步：最小证据闭环

一次有效定位，必须同时拿到四样，缺一不可：

1. **丢包瞬间的 CPU 利用率**（区分控制面/转发面）
2. **丢包瞬间的端口统计**（CRC/错包/出方向丢弃计数）
3. **双向抓包**（request 到没到、reply 回没回）
4. **PC-PC 对比测试**（隔离终端嫌疑）

## 三、实战案例：IE4120U ping 中断

> 客户案例：弱管交换机 IE4120U-28TP 下挂 PC 周期性丢包。完整演示上面六步框架的落地。

### 3.1 现象

1. 核心网关 ping 终端，IE 与终端直连端口抓包：终端没回 request，疑似终端问题。
2. 核心网管 ping PC，PC 上抓包：PC 没回 request，疑似 PC 问题。
3. **多个 IE4120U 下挂设备都出现同样丢包**。
4. 抓包报文**从第 40 个左右开始丢包，然后恢复**。

### 3.2 组网

```
核心(ITC) → 汇聚 IE4320-28F(10.140.50.183，ping源) → 接入 IE4320-28S → IE4120U(弱管) → PC(10.140.50.201)
```

- ping 命令：`ping -a 10.140.50.183 -c 100 10.140.50.201`，interval 200ms，timeout 2000ms
- 结果：100 发 96 收，4% 丢包，丢 seq 39~42；seq 43 的 RTT 突然 519ms

### 3.3 抓包还原的硬事实（pcapng 解析）

| 项目 | 数值 | 说明 |
|:-----|:-----|:-----|
| 抓包点 | 目标 PC 本机 | Wireshark + Npcap，Windows 11 |
| 丢包序号 | seq 39/40/41/42 | "第 40 个左右"（seq 从 0 计） |
| 故障窗口 | 约 9.3 秒 | seq39 发出到 seq43 回复 |
| seq43 回复延迟 | 518ms | 正常仅 0.07ms |
| ARP 报文 | 7224 个，78.8 个/秒 | 全程高位，异常 |
| 报文对比 | request 全程无差异 | 源 MAC/TTL/VLAN 一致 |

### 3.4 排查过程（假设 → 验证 → 收敛）

| 阶段 | 假设 | 验证方式 | 结果 |
|:-----|:-----|:---------|:-----|
| 1 | 终端/PC 有问题 | PC 侧抓包 | ❌ PC 不是不想回，是发了 8 次 ARP 回不了 |
| 2 | 报文异常/路径变化 | 对比正常 vs 丢包的 request | ❌ 报文完全无差异，排除 |
| 3 | 汇聚交换机(183) CPU 被打满 | 看 183 回复延迟 | ❌ 183 收到请求 0.9ms 秒回，不慢 |
| 4 | **IE4120U 转发被拖垮** | 绕开 IE 不丢包 + IE 下只 3 终端 | ✅ 锁定 IE 这一跳 |
| 5 | ARP 风暴源头 | 抓包按 OUI 统计 | ✅ 飞利浦 `00:17:88` 设备全网段扫描 |

### 3.5 最终根因链

```
飞利浦照明设备(00:17:88 OUI) 对 10.140.50.0/24 做 ARP 扫描
   → 海量 ARP 广播泛洪到整个 VLAN，灌进 IE4120U
   → IE4120U（弱管机）广播转发/CPU 被拖垮
   → PC 的 ARP 请求（问 183）在 IE 这一跳被延迟 8 秒才转发出去
   → 183 收到后 0.9ms 秒回（抓包铁证：REPLY sender=183）
   → PC 8 秒后才拿到 183 的 MAC，才能回 ICMP
   → seq 39~42 丢包；绕开 IE，8 秒延迟消失，不丢
```

### 3.6 关键证据（抓包铁证）

1. **回复者是 183，不是 IE4120U**：`REPLY sender=10.140.50.183(5c:f7:96:75:f8:00)`。IE 是二层转发"搬运工"，不回复"谁是 183"。
2. **183 不慢**：收到 PC 第 8 次 ARP 请求后 0.9ms 就回，慢的是"请求到达 183 之前"的 IE 转发段。
3. **风暴源头 OUI**：所有疯狂 ARP 的源 MAC 都是 `00:17:88`（飞利浦照明），且在**同一毫秒内顺序扫描一串 IP**（.15/.23/.25/.29/.41/.51...），典型全网段 ARP 扫描。
4. **绕开 IE 不丢包**：控制变量法直接证明问题在 IE4120U 这一跳。

### 3.7 方法论落地对照

| 方法论步骤 | 本案体现 |
|:-----------|:---------|
| 转发面 vs 控制面 | 交换机 ping 终端，两次穿越 CPU，CPU 忙必丢 |
| 双向抓包 | PC 侧抓包 + 上下联口对比，锁定 ARP 转发延迟 |
| 报文对比（阴性结果也有效） | 排除 MAC 变化/路径变化/VLAN 变化 |
| 逐跳隔离 | "绕开 IE 不丢包"一刀定位到 IE 这一跳 |

## 四、面试话术 + 诚实边界

**面试话术**：

> "我排查网络丢包有一套固定套路：先分清是转发面还是控制面的问题——交换机自己 ping 和 PC 之间 ping 走的路径完全不同，搞错方向就是白忙。然后自底向上分层排查，物理层看错包、链路层看 STP 和 MAC 表、控制面看 CPU。最关键的是双向抓包，单点抓包一定会误判。
>
> 客户反馈弱管交换机下挂的 PC 周期性丢包，一开始都怀疑是终端问题。我没急着下结论，先解析了 PC 侧抓包，发现 PC 在丢包窗口里发了 8 次 ARP 请求问网关 MAC，8 秒没人回——说明 PC 不是不想回，是回不了。再对比正常和丢包的报文完全一致，排除了报文异常。最后用控制变量法让客户绕开交换机一测，不丢包了，锁定是这台弱管交换机被上游的 ARP 广播风暴拖垮了转发。抓包按 MAC 的 OUI 一查，风暴源头是飞利浦的照明设备在全网段做 ARP 扫描。整个过程就是'假设→抓包验证→收敛'，每一步都有证据。"

**诚实边界**：

- 本案最后"IE4120U 转发延迟"的完整实锤，还差**上下联口同时抓包**这一步（区分"请求没上去"还是"reply 没下来"），当前结论是"绕开不丢包"的强推断 + 抓包间接证据。
- 面试若被追问细节，如实答：定位到"IE 这一跳 + 风暴源头"，IE 内部是 CPU 打满还是风暴抑制触发，需现场抓 IE 的 CPU 利用率和上下联口包流进一步确认。

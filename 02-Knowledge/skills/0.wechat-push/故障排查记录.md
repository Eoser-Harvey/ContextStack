# WeChat 推送故障排查记录

## 核心问题：微信 Bot 会话无法持久保持（2026-06-18 定论）

### 根本原因
**mcp-wechat-server 使用微信开放平台「个人号机器人」协议，本质上是模拟网页微信登录。**
- 微信网页版协议对长时间不活跃的会话会主动断开
- bot 只能**回复**已建立会话的用户消息，不能主动发起新会话
- 会话断开后，`send_text_message` 仍然返回 `sent`，但微信服务器实际丢弃了消息
- 必须用户先发一条消息给 bot，才能重新建立会话通道

### 这就是为什么：
1. 每次重新扫码后 botId 变化 → user ID 不变但通道需要"激活"
2. 09:24 扫码登录后发送 5 条消息全部"sent"但用户收不到 → 因为用户没先发消息激活通道
3. 09:39 用户发了"test"后，bot 才能正常回复 → 通道被激活

## 彻底解决方案对比

| 方案 | 原理 | 24h稳定性 | 是否需用户操作 | 推荐 |
|------|------|-----------|---------------|------|
| **A. Server酱/企业微信Bot** | Webhook推送 | ✅ 极高 | ❌ 一次配置 | ⭐⭐⭐ |
| **B. 微信个人号保活** | 心跳+定时激活 | ⚠️ 中等 | ⚠️ 可能仍需扫码 | ⭐⭐ |
| **C. Telegram Bot** | Bot API | ✅ 极高 | ❌ 一次配置 | ⭐⭐⭐ |
| **D. 钉钉/飞书 Bot** | Webhook | ✅ 极高 | ❌ 一次配置 | ⭐⭐⭐ |

### 推荐方案：Server酱（最省心，已配置）

**你已有 Server酱 配置**（`x_tweets/config.yaml` 中有 `server_chan.send_key`）。
- 原理：HTTP POST → 微信模板消息 → 你的微信
- 优点：不依赖扫码登录，不会断开，24h稳定
- 缺点：免费版有次数限制，Turbo版 ¥20/月无限次

**改造步骤：**
1. 获取 Server酱 SendKey（https://sct.ftqq.com/）
2. 每次推送时，先尝试 IDE WeChat MCP（如果通道激活中）
3. MCP 失败 → 自动 fallback 到 Server酱 HTTP 推送
4. 双通道保障：MCP 正常时用 MCP，MCP 断时用 Server酱

## 当前通道激活规则（已确认）

```
用户先发消息给 bot → bot 才能回复 → 通道激活
通道激活后 → 可以持续发送（直到会话过期）
会话过期时间 → 不确定（微信网页版通常几小时到一天）
```

### 保活策略
如果坚持用 WeChat MCP：
- 每小时推送前，先发一条心跳消息给 bot（模拟用户操作）
- 或者设置一个独立脚本，每 30 分钟用 `get_messages` 保持长连接

## 2026-06-18 保活进程方案验证结论：不可行

### 测试结果
- 保活进程正常运行（每30秒 get_messages 心跳）
- channel_state.json 显示 keepalive_alive=true
- 但 11:40 和 13:20 的推送消息用户均未收到

### 根因
**微信 Bot 的接收通道（get_messages）和发送通道（send_text_message）是独立 session。**
保活进程只能保持接收通道的长连接，但发送通道仍会在空闲后断开。

### 最终结论
微信个人号 Bot 无法做到真正的 24h 无人值守。
唯一可靠方案是换用 Webhook 类推送通道（企业微信 Bot / Server酱 / Telegram）。

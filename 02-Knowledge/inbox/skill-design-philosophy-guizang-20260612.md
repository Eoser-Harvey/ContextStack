## 一、核心判断：Agent 放大差距，而非抹平

- 头部用户已默认理解 Agent 组成要素：文档、规则、memory、loop、MCP、CLI、工具调用、权限、安全沙箱、上下文工程、定时任务、心跳、文件系统、代码执行、Skill
- 普通用户只知道"Agent 能写代码"
- **K 型分化**：去年可靠产品设计能弥合差距，今年已很难靠简单 UX 解决

> 对 ContextStack 的启示：我们属于"头部用户"侧，应充分利用 Skill 能力，而非等待 UX 层简化。

---

## 二、Skill 的核心定义

**Skill = 把专家经验、工作流、品味和工具调用封装成可分发、可复用、可迭代的 Agent 能力单元。**

三层对比：
| | 提示词 | Skill | 传统 App |
|---|---|---|---|
| 可复制性 | 极易复制 | 工程化打包 | 需安装 |
| 版本管理 | 无 | 有（迭代） | 有 |
| 分发能力 | 弱 | 强（跨平台） | 平台绑定 |
| 含专业经验 | 弱 | 强（固化判断） | 看设计 |

**关键洞察**：很多任务是一组稳定流程（读取→分析→选择→调用→生成→验证→修复→导出），Skill 把流程从一次性对话中抽出来。

---

## 三、Skill 的本质：人的经验外化

作者案例说明真正有价值的部分：
- PPT Skill：固化版式判断、设计系统经验、模板选择
- 社交媒体卡片 Skill：28 个版式骨架，先被人验证，AI 只负责填充
- Logo Generator：分层处理（本体/展示/交互），不让图像模型一把梭

**创作者需同时懂三件事**：
1. **传统专业知识**（知道什么算好）
2. **AI 的上下限**（知道什么能做、什么必须兜底）
3. **产品化思维**（知道用户场景和门槛）

---

## 四、用户视角：不关心概念，只关心结果

对普通用户而言，Skill/MCP/CLI/Plugin 叫什么不重要，重要的是：
- 能解决什么问题
- 适合什么场景
- 点一下能不能用
- 结果长什么样
- 别人用得怎么样

> 产品层应弱化概念、强调功能。

---

## 五、好 Skill 的架构原则

### "中心短，辐射厚"
```
SKILL.md          ← 只放高信号流程和判断
references/       ← 重文档
scripts/          ← 确定性逻辑
assets/           ← 模板和示例
```

### description 是路由触发器
- 不是宣传语，而是描述"用户什么时候需要它"
- 先调 description，确保该加载时加载

### Thin Harness, Fat Skills
- 底层运行环境保持轻量
- 能力放在按需加载的 Skill 里

---

## 六、Skill 质量维护生命周期

**六步法**：

1. **先用无 Skill 的 Agent 跑真实任务**，找它会错在哪里
2. **基于真实 query 写 eval**（正例、反例、forbidden load）
3. **先调 description**，确保该加载时加载
4. **写主体时只保留会改变模型行为的判断**——每句内容问"没有这句 Agent 会不会做错？"不会就删
5. **把失败案例追加到 gotchas**——gotchas 是最高价值内容，来自真实失败
6. **跨模型测试**

> 核心原则：gotchas > 正向说明，来自真实失败的经验最值钱。

---

## 七、设计类 Skill 的核心理念

**把专业品味变成模型可执行的限制**——替用户排除绝大多数会变丑的选项。

具体约束：
- 不使用纯白和纯黑
- 不让用户任意输入 hex，只提供验证过的主题色板
- 版式骨架先被人工验证，AI 负责填充、组合和微调
- 把 AI 任务从"自由设计"降级成"在高质量骨架里填充"

## 八、Skill 生态与分发

| 渠道 | 适合内容 | 特点 |
|---|---|---|
| **GitHub** | 代码型 Skill | 基础分发、跨平台覆盖 |
| **小红书** | 视觉内容、使用案例 | 传播力强 |
| **应用商店式** | 精准推荐、低门槛 | 创作者分成潜力 |

**防盗用策略**：开源覆盖更多平台 + 持续迭代 + 自媒体让用户知道源头 + 社区案例形成品牌资产。

---

## 九、普通用户的真正卡点

不是不能用 Skill，而是**交互心智**问题：
- 仍用传统软件思维，以为一次生成就该完成
- 不习惯通过 chat 连续调整

**行业 Skill 是重要方向**：健身、法律、餐饮、活动策划、教育等，每个行业都有先锋用户值得优先服务。

## 十、Skill 的边界扩展

Skill 不会局限在聊天框里，会扩展到：
- 浏览器
- 桌面
- 本地文件
- 硬件
- 内容平台
- 游戏引擎
- 真实工作环境

---

## 十一、Skill vs Gene/Capsule

| | Skill | Gene/Capsule |
|---|---|---|
| 创建方式 | 人类预先沉淀 | 从运行中自动长出 |
| 特征 | 明确创建者、边界、流程、版本 | 带成功率、变异历史、自动修复 |
| 关系 | 人定义品味和边界 | Agent 收集证据、补充 eval、维护长尾 |

**理想形态**：人定义品味和边界，Agent 负责收集证据、补充 eval 和维护长尾经验。

---

## 十二、平台建议

做好 Skill 平台的前提是先做好 Agent 基础体验：
1. 多模型支持
2. 文件/项目/内存管理
3. 权限安全
4. 长程任务
5. 多设备流转
6. 官方高质量插件开箱即用

---

## 十三、关键技术术语表

| 术语 | 解释 |
|------|------|
| **Skill** | 把提示词、流程、工具调用、模板、脚本、边界和经验打包的可复用能力单元 |
| **Memory** | Agent 用来保存长期偏好、项目状态和历史决策的外部记忆 |
| **Loop** | Agent 反复"思考→调工具→观察结果→再决定下一步"的执行循环 |
| **MCP** | Model Context Protocol，让 AI 以统一方式连接外部工具/数据源的协议 |
| **SKILL.md** | Skill 的入口说明文件，告诉 Agent 何时加载、按什么流程执行、哪些坑不能踩 |
| **Harness** | 运行 Agent 的外层程序，负责模型循环、文件读写、上下文管理和安全边界 |
| **Thin Harness, Fat Skills** | Agent 底层轻量化，能力放在按需加载的 Skill 里 |
| **Eval** | 用真实/模拟任务测试 Skill 是否按预期触发和执行的评估 |
| **Gotchas** | 从真实失败中总结的"别这么做"清单，比正向说明更能提升稳定性 |

## 十四、对 ContextStack 的启发

1. **Skill 架构**：当前 inbox 文档整理流程已接近一个"隐式 Skill"，可考虑显式化为 SKILL.md + references/ 结构
2. **Gotchas 机制**：在会话模板中增加"本次踩坑"板块，逐步积累项目级 gotchas
3. **路由描述**：各 Skill 模块的 description 应改为"触发场景描述"而非"功能宣传"
4. **Thin Harness 原则**：ContextStack 框架本身保持轻量，能力通过按需加载的 Skill/知识模块提供
5. **行业 Skill 机会**：嵌入式开发、H3C 网络设备调试等垂直领域有 Skill 化潜力

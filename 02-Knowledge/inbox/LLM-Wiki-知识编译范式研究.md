---

## 一、核心洞察：从"查询时综合"到"持续知识编译"

**传统 RAG 的缺陷**：上传文件 → 查询时检索片段 → 生成答案。每次提问都从零重新推导，没有积累。问一个需要综合 5 份文档的问题，模型每次都要重新找、重新拼。**知识死在聊天记录里。**

**LLM Wiki 的做法**：LLM 增量构建并维护一个**持久化 Wiki**——位于原始资料和你之间的一层结构化、互相链接的 Markdown 文件。新增资料时，LLM 不只是索引，而是读取、提取关键信息、**并入现有知识网络**：更新实体页、修订主题摘要、标记新旧矛盾、强化或挑战演化中的综合结论。

> 知识被编译一次，然后持续保鲜——而不是每次查询重新推导。

**关键类比**：
> Obsidian 是 IDE，LLM 是程序员，Wiki 是代码库。

---

## 二、三层架构

| 层 | 内容 | 谁拥有 |
|----|------|--------|
| **Raw Sources** | 原始资料（文章/论文/会议纪要），**不可变**，LLM 只读不改 | 你（事实源） |
| **Wiki** | LLM 生成的 Markdown 页面：摘要/实体/概念/综合/对比/时间线/矛盾 | LLM 全权维护 |
| **Schema** | 规则文件（AGENTS.md / CLAUDE.md），规定目录结构、命名、frontmatter、引用格式、工作流 | 你与 LLM 共同演化 |

---

## 三、三大工作流

### 1. Ingest（摄入）—— 新资料"并入"而非"入库"
1. 阅读资料，提取标题/作者/日期/核心论点
2. 创建 source summary 页
3. 查找并更新相关实体页、概念页、综合页
4. 新概念 → 新建概念页
5. **新资料推翻旧结论 → 不覆盖，先标记 contradiction**
6. 更新 index.md，追加 log.md

### 2. Query（查询）—— 好答案写回 Wiki
- 先读 index.md 定位页面 → 读相关页 → 综合回答（区分事实/综合/推断/不确定）
- **高价值答案（对比表、架构梳理、路线图、新关系、待研究问题）要写回 Wiki**，不留在聊天记录里
- 查询不只是消费知识，也是生产知识

### 3. Lint（体检）—— 知识库的静态分析
- 孤岛页面（无入链/出链）、重复概念、缺失引用、过期结论、冲突未处理、索引漂移
- 小型个人 Wiki 每周一次即可

---

## 四、两个特殊文件

| 文件 | 性质 | 作用 |
|------|------|------|
| **index.md** | 内容导向 | 全库目录：每页一行链接+一句话摘要，按类别组织。LLM 查询时先读它定位。**~100 sources / 数百页规模下，比向量库更可靠** |
| **log.md** | 时间导向 | append-only 演化记录。每条以 `## [日期] ingest \| 标题` 开头，可用 `grep` 解析 |

---

## 五、检索策略：不急着上向量库

1. **第一阶段**：index.md + 文件系统搜索（100 sources 以内够用）
2. **第二阶段**：BM25 + frontmatter 过滤（按 type/status/updated/tags/confidence 过滤）
3. **第三阶段**：向量搜索 + MCP 工具化（数千页才需要；索引是加速器，不是 source of truth）

---

## 六、质量控制（社区实践精华）

**风险：幻觉被长期保存** —— 聊天里的幻觉影响一次回答，Wiki 里的幻觉影响未来所有回答。

**核心原则：No citation, no claim（无引用，不主张）**
- 没有证据链的内容只能作为假设，不能作为结论
- 推断必须标记为 inference
- 低置信度页面写清不确定性

**冲突是一等公民**：不要急着抹平矛盾。记录双方观点+来源，创建 contradiction 页，说明可能原因（时间/范围/定义/测量方法），标记什么证据能解决冲突。

## 七、真实案例：韩国会计师的实践（2026-07 评论）

非开发者、非英语母语者，用 LLM Wiki 维护会计标准+IT+物理+数学+哲学多领域知识库。两个关键扩展：

1. **每页验证状态（verification status）**：AI 生成内容先进"隔离收件箱"，标记 `unverified`，**在对照原始资料逐段核实前，不能被其他页面引用**。未验证页引用未验证页 = 审计师拒绝的循环证据。
2. **外部聊天对话是一等摄入源**：用标准化 prompt 把 ChatGPT/Claude 对话蒸馏成原子笔记，走同一个隔离收件箱流程。

## 八、对你 ContextStack 的借鉴分析

### 现状诊断：你正处于"RAG 模式"

你的 `02-Knowledge/inbox` 已有 **87 个归档文件**，流程是：粘贴文章/链接 → 我归档成 md → 进 inbox。这正是 Karpathy 说的"原始资料积累层"，但**缺少编译层**：
- 文件之间没有交叉链接（梁文锋 52 条和 YC 报告、麦肯锡消费报告之间没有关联）
- 没有 index.md 内容地图，找资料靠记忆
- 好的分析结论（如"MRVL 卖出信号待定义"）散落在聊天记录里，没有沉淀成可复用页面
- 没有矛盾追踪（如投资策略里"待定义"的卖出信号，就是未解决的 contradiction）

### 可借鉴的 5 件事（按性价比排序）

**1. 建 index.md（最高价值，最低成本）**
给 inbox 建一个内容地图，按类别（投资/职业/成长/技术/角色榜样）列出每篇一句话摘要。之后每次归档自动更新。87 篇规模正好适用。

**2. 查询写回（Query write-back）**
以后我给你的分析（投资复盘、行业判断、机会分析）如果产生可复用结论，沉淀成独立页面，而不是只留在对话里。你已有的 `investment-strategy.md` 就是雏形——它记录了"MA120 卖出信号待定义"这类演化中的结论。

**3. 矛盾追踪（contradiction）**
投资策略文档里"待定义"的卖出信号、CRCL 目标价 vs 实际走势的偏离，都应该显式记录为"未解决矛盾"，而不是悄悄覆盖。你的记忆系统已经隐含这个（"Factual information must be validated"），可以显式化。

**4. Schema 已有雏形，可强化**
你的 `.trae/rules/框架约束.md` 就是 Schema 层！它已经规定了 Git 用户、归档位置、Feishu 推送等规则。可以补充"归档工作流"规则：每次归档时更新 index.md、标记验证状态、记录矛盾。

**5. 验证状态（来自会计师案例）**
你的记忆里已有"未经验证的事实不能呈现"原则。可以给归档文件加 frontmatter 验证状态（verified/unverified），特别是投资相关的事实（价格、持仓、新闻）。

### 不建议照搬的
- **向量库/MCP 搜索**：87 篇规模完全不需要，index.md 足够
- **Obsidian 生态**：你用的是 TRAE + Git + 记忆系统，不是 Obsidian。借鉴的是**模式**（三层架构+三大工作流），不是工具
- **纯 LLM 全权维护**：你的投资/财务数据需要人工把关，LLM 只做草稿

---

## 九、一句话总结

> 你已经有 Raw Sources（inbox）和 Schema（框架约束.md），缺的是中间那层 **Wiki**——一个由 index.md + 交叉链接 + 矛盾追踪组成的编译层。补上它，87 篇归档就能从"堆积"变成"复利"。
